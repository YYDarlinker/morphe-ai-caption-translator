## 0. 一句话结论

四个问题不是四个孤立的 UI/文案/模型问题，而是同一类**权威错位**的四个出口：

1. **语种**：YouTube 的“自动默认轨道”被当成了用户选择，覆盖了 `CaptionChoice` 和当前翻译会话；真正的跨视频记忆 `RememberedCaptionSelection` 只在一个原生默认轨道选择器里被查询，既不参与 timed-text URL 决策，也没有否决权。附加语种的克隆又把 `language` 硬编码成 `zh-Hans`，使记忆身份进一步绑定简体中文。
2. **标签**：菜单标签有三个互不统一的来源（YouTube 原生 `displayName`、ICU `Locale.getDisplayName`、应用资源 `cap_language_zh_hant`），优先级是“原生 > ICU > 应用资源”。诊断期间选中的两个语种本来就存在于原生菜单，因此扩展根本没有插入新条目，应用自己的“中文（繁体）”标签永远没有机会出现。
3. **翻页**：自动字幕的 srv3/XML 片段计时在 `CaptionDocument` 里已经被解析出来，却在 `RebuildSource` 的通用回退分支里被丢弃；随后 `RebuildController` 又用 `nativeWordCount() > 0` 作为“要不要去取 ASR 计时参照”的门槛，于是 native=0 时反而**完全不取参照**。页面时间只能在粗 cue 窗口内按阅读量均摊，翻页位置必然漂移。
4. **人工字幕翻译质量**：人工轨被“一字幕一请求块”切分（400 cue = 400 个 API 请求），提示词要求“一个 cue 一个 event，邻句只作上下文”；模型没有机会把跨 cue 的半句合成自然句。更严重的是，语义/目标语言校验被 `canApplyEnglishToChinese` 门禁限制，`ja → zh-Hans` 完全不校验，模型把日文原样返回也会被接受。

修复方向因此不是改四个字符串或四个阈值，而是把**用户意图、轨道身份、计时证据、翻译单元**四件事各自单一化（见第 6 节）。

## 1. 问题一：语种记忆永远回到简体中文

### 1.1 用户期望与代码现状

期望：某个视频里选了英文后，只要本次 YouTube 进程不重启、用户不再改，后续视频自动打开字幕并沿用英文；如果新视频本身有英文轨，直接显示、不调用 API。

代码里实际存在**三个独立的“当前语言”权威**：

| 权威 | 生命周期 | 写入者 | 读取者 |
|---|---|---|---|
| `CaptionChoice` | 进程级，但被当作“当前视频” | `applySelection()` 每次原生轨道应用 | `DeepSeekConfig.defaultTargetLanguage()`、prewarm、`CaptionVideoHandoffV2` |
| `RememberedCaptionSelection` | 进程级，只在显式 `PREFERRED_TRACK` 时写入 | `followNativeSelection()` | 只有 `NativeCaptionBridge.resolveRemembered()` |
| `CaptionVideoHandoffV2` | 12 秒 pending | `onVideoId()` 时捕获 | 新视频第一次 timed-text 请求 |

这三者没有仲裁关系。用户选了英文后：

- `RememberedCaptionSelection` 确实变成 `en`；
- 但新视频的原生默认事件 `reason=2;origin=DEFAULT;track=zh-Hans` 到来时，`applySelection()` 会启动 zh-Hans 会话；
- 当前工作树的 `applySelection(track, true)` 还会把 `CaptionChoice` 覆盖成 `zh-Hans`；
- 新视频第一次 timed-text 请求到来时，`CaptionVideoHandoffV2` 读的是 `DeepSeekConfig.defaultTargetLanguage()`，也就是被覆盖后的 `zh-Hans`，不是记忆里的 `en`。

### 1.2 直接证据：诊断时间线

同一份诊断里，用户在 `FzRyrjFmZSQ` 上明确选英文，随后自动默认事件把引擎切回简体：

| 时间（uptime ms） | 事件 | 含义 |
|---|---|---|
| `1792389373445` | `NATIVE_TRACK_APPLIED ... reason=1;origin=PREFERRED_TRACK;track=en/manual` | 用户显式选择英文 |
| `1792389373500` | `LANGUAGE_PROFILE_BOUND session=154; target_code=en` | 英文会话启动 |
| `1792389428164` | `NATIVE_TRACK_APPLIED ... reason=2;origin=DEFAULT;track=zh-Hans/manual` | 原生默认简体事件 |
| `1792389428221` | `LANGUAGE_PROFILE_BOUND session=195; target_code=zh-Hans` | 同一视频被切回简体 |
| `1792389439068` | `NATIVE_TRACK_APPLIED ... foreground=false; reason=2;origin=DEFAULT;track=zh-Hans/manual` | 下一个视频 `mH5TlcMo_m4` 的后台默认简体 |
| `1792389439131` | `LANGUAGE_PROFILE_BOUND session=226; target_code=zh-Hans` | 新视频以简体开始 |

整份 10,839 条事件的诊断里，**没有一次 `VIDEO_DEFAULT_AI_RESTORED`**。也就是说，唯一为跨视频语言准备的 handoff 根本没有成功执行；新视频看到的是 YouTube 原生默认（本机/本账号为简体），不是用户的英文。

### 1.3 可复现实验：克隆身份 + 自动默认覆盖

`validation/runs/20261019-root-cause/TmpMemoryProbeTest.java` 用生产 `NativeCaptionBridge` 和真实 `DeepSeekConfig` 跑出：

```text
SELECTED added-English target=tlang=en but track.language=zh-Hans -> remembered.language=zh-Hans translated=true decision=1
SELECTED native-English -> remembered.language=en
before automatic default: CaptionChoice=en remembered=en
after automatic zh-Hans default: CaptionChoice=zh-Hans remembered=en defaultTarget=zh-Hans
```

两行就是两个独立根因：

1. **克隆轨身份错误**：`bindCloneTranslation` 把所有新增翻译轨的 `language` 字段固定写成 `"zh-Hans"`，只把 `displayName`、`url.tlang`、`vss` 改成用户选择的语种。用户从新增菜单项选英文时，URL 是 `tlang=en`，但 `language(track)` 返回 `zh-Hans`；`CaptionChoice`、`RememberedCaptionSelection` 都记成简体。
2. **自动默认覆盖**：`applySelection(track, explicit || (!off && !CaptionChoice.userOff()))` 让 `origin=DEFAULT` 的自动简体事件也以 `remember=true` 执行，`CaptionChoice.select("zh-Hans", true)` 覆盖了用户显式的英文。`RememberedCaptionSelection` 仍是 `en`，但 handoff 读的是 `CaptionChoice`，所以 `defaultTarget=zh-Hans`。

### 1.4 更深一层的代码原因

#### A. handoff 的设计目标本身是“语种只属于本视频”

`application-host/.../CaptionVideoHandoffV2.java:6-13` 的类注释写得很明确：

> A language chosen from YouTube's Auto-translate menu belongs to that video only. When a real
> video-id change happens ... the next video's first timed-text request is allowed to restore the
> configured default AI target exactly once.

它恢复的是 `DeepSeekConfig.defaultTargetLanguage(context)`（`:68`），不是
`RememberedCaptionSelection.language()`。这行代码与用户期望的“沿用上次选择的语种”是相反的：
它只会把新视频拉回“当前默认/原生默认”，而不是上次的用户选择。

`DeepSeekConfig.defaultTargetLanguage()` 的实现（`infrastructure/.../DeepSeekConfig.java:252-254`）是：

```java
return CaptionChoice.isOn() && CaptionChoice.translates() ? CaptionChoice.language() : "";
```

它读的是**当前视频的 `CaptionChoice`**。当新视频的原生默认事件先把 `CaptionChoice` 覆盖成
`zh-Hans`，handoff 自然只能恢复 `zh-Hans`。这就是“永远简体”的直接闭环。

另外，`CaptionVideoHandoffV2.onVideoId()`（`:30-35`）只有
`CaptionAddonSupport.memoryInstalled() && CaptionChoice.isOn()` 时才武装 pending。如果安装 APK 时没有选
Remember 补丁，或切换视频时 `CaptionChoice` 已不是 ON，handoff 根本不会执行；这一点在诊断里无法区分，
因为导出没有记录 `memoryInstalled()`/`CaptionChoice` 状态。它使“没有 restore 事件”有两个可能：没武装，
或武装了但被 `mayActivateAiTarget()`/target 判断清掉；两者都不改变“读的是 defaultTarget 而非记忆”的结论。

#### B. 记忆只在“原生默认轨道选择器”里被查询，没有否决权

`NativeCaptionBridge.resolveRemembered()`（`:687-703`）只在 patch 注入的
`findDefaultTrack` 选择器里被调用。它返回一个 `translatedTracks` 中语言相等的轨道，供
YouTube 初始化默认轨道。问题在于：

- 它不是 timed-text URL 重写的一部分；
- 它不会在 `followNativeSelection()` 看到 `origin=DEFAULT` 的简体事件时说“等等，用户记忆是英文”；
- 新视频的默认轨道可能由 YouTube 自己的持久状态给出，不经过这个选择器；
- 一旦简体事件已经应用，`applySelection()` 就启动简体会话，记忆不再有机会。

诊断里的 `reason=2;origin=DEFAULT` 事件正是这条“绕过记忆”的路径。

#### C. 克隆轨硬编码 `zh-Hans`

`patches/.../NativeCaptionBridgePatch.kt:297-321`：

```smali
const-string v1, "zh-Hans"
invoke-virtual {v0, v1}, languageSetter
```

`translationUrl` / `translationVss` / `translationLabel` 都按真实目标 code 生成，唯独
`language` 字段固定为简体。这个字段正是 `CaptionChoice.select()`、`RememberedCaptionSelection.select()`、
`resolveRemembered()`、`CaptionLanguageSelection.canonical()` 的输入。结果是**任何新增语种都被记忆成简体**。
这也解释了为什么用户会觉得“绑定简体中文”——只要它选过任何一个扩展新增的语言，下一次
`resolveRemembered` 都会去找 `zh-Hans`，并命中 YouTube 原生的简体轨。

同一个错误还会破坏菜单幂等：`augmentTranslations()` 用 `canonical(language(track))` 判断“是否已存在”。
克隆轨的 `language` 是 `zh-Hans`，而用户选的 code 是 `fr`/`zh-Hant`/`en`，下一次菜单构建会认为该 code
不存在，再次插入同名克隆；这就是“单次菜单打开只能产生一次每种新增语言”的反例。本次诊断里没有触发，
只是因为选中的两个 code 本来就在原生列表里（见第 2 节）。

#### D. 空 code 的默认值是简体

`caption-shared/.../TargetLanguage.java:97-105`：

```java
static TargetLanguage fromCode(String rawCode) {
    String code = normalize(rawCode);
    if (code.isEmpty()) return SIMPLIFIED_CHINESE;
    ...
}
```

空/未知 code 不被当作“未知”，而是当作 `zh-Hans`。在 prewarm、诊断等路径上，这会把“没有选择”
静默变成“选择简体”。它不是本次现象的唯一原因，但属于同一默认偏置，且会让“无记忆”与
“记忆简体”在行为上不可区分。

### 1.5 为什么“视频自带目标译文时不调用 API”不能证明记忆有效

`SourceTrackPolicy.ownTargetTrack()`（`application-host/.../SourceTrackPolicy.java:126-155`）在
`DeepSeekCaptionHook.rewriteUrl()` 的请求路径上：只要**当前请求的 tlang** 与视频已有轨道同书写语言，
就直接显示该轨道，不调用 API。它只依赖当前请求的 target code，与 `RememberedCaptionSelection` 无关。
因此这个机制工作正常，并不代表跨视频记忆工作正常；两者恰好是同一请求路径上的两个独立判断。

### 1.6 根因归纳

- **R1-1（直接）**：`origin=DEFAULT` 的自动原生默认被当作可记忆选择，覆盖 `CaptionChoice`；当前工作树的
  `applySelection(track, explicit || (!off && !CaptionChoice.userOff()))` 是这一覆盖的入口。
- **R1-2（结构）**：`RememberedCaptionSelection` 没有请求路径上的仲裁权；它只在原生默认轨道选择器里被查询，
  无法否决已经应用的原生默认。
- **R1-3（设计）**：`CaptionVideoHandoffV2` 明确把语言定义为“本视频”，恢复的是 `defaultTargetLanguage`（当前
  `CaptionChoice`），不是记忆；当 `CaptionChoice` 被覆盖后，它恢复的必然是简体。
- **R1-4（身份）**：克隆轨 `language` 固定 `zh-Hans`，把所有新增语种的身份污染成简体；空 code 又默认简体。

> 版本边界：`applySelection` 的覆盖行为是当前工作树的未提交修改。tag `2c96054` 的版本是
> `applySelection(track, off || explicit || !CaptionChoice.known() || !CaptionChoice.isOn())`，自动默认不会覆盖
> `CaptionChoice`，但它仍然会**启动**简体会话；而 handoff 是否成功还取决于 `mayActivateAiTarget()` 与
> video-id 回调时序。也就是说，R1-2/R1-3/R1-4 在发布版就存在，R1-1 让“永远简体”在当前工作树中变成确定性结果。
> 若要在真机上完全闭环，应先核对安装 APK 中 `applySelection` 的分支。

### 1.7 修复方向（已在 `N40-REPAIR-20261019.md` 实施）

1. 把“用户显式选择”和“原生自动默认”分成两个状态；自动默认只能作为**建议**，不能覆盖显式选择。
2. 在 `DeepSeekCaptionHook.rewriteUrl()` 的 timed-text 请求路径上读取记忆，而不是只依赖原生默认轨道选择器；
   记忆存在时，显式选择优先于原生默认。
3. `CaptionVideoHandoffV2` 恢复 `RememberedCaptionSelection.language()`（并按 `translated/asr` 匹配轨道），
   或者删除这个 handoff，统一由记忆层接管。
4. `cloneTranslation` 必须把 `language` 设为真实 `code`；`TargetLanguage.fromCode("")` 应返回“无目标”而不是简体。
5. 增加 `LANGUAGE_MEMORY_*` 诊断，至少记录 memory decision/language、当前轨道、覆盖原因、handoff 是否命中。

## 2. 问题二：新增“中文（繁体）”在语种菜单显示为“中文（繁体中文）”

### 2.1 先区分两个菜单

- **设置页多选**：`CaptionLanguagesPreference.languageLabel()`（`ui/.../CaptionLanguagesPreference.java:139-143`）
  对 `zh-Hant` 使用资源 `cap_language_zh_hant`。中文资源值是 `中文（繁体）`（`values-zh-rCN`），
  这里没有“中文（繁体中文）”。
- **YouTube 自动翻译菜单**：条目来自 YouTube 的 track 对象/元数据，标签由
  `NativeCaptionBridge.translationLabel()` 或原生 `displayName` 决定。用户看到的冗余标签只可能来自这里。

### 2.2 诊断证明：扩展根本没有插入这个语种

2026-10-19 的 7 份 1.5.4 诊断中：

- `LANGUAGE_MENU_READY` 共 60 次；
- `LANGUAGE_MENU_INSERTED` **0 次**；
- 当前文件 43 次 `LANGUAGE_MENU_READY`，典型值为 `selected=2;items=3`，也有 `items=17/18/19`。

`augmentTranslations()` 只有在 `present.add(code)` 成功（即原生列表里没有这个 code）时才
`cloneTranslation()` 并记 `LANGUAGE_MENU_INSERTED`。0 次插入说明：**用户选中的两个语种本来就在
YouTube 原生翻译列表里**。因此菜单里那一项是原生对象，标签是 YouTube 的原生标签；扩展的
`cap_language_zh_hant` 从未参与。

### 2.3 标签优先级：原生 > ICU > 应用资源

`NativeCaptionBridge.translationLabel()`（`application-host/.../NativeCaptionBridge.java:124-127`）：

```java
String name = labelsCurrent() ? nativeLabels.get(code) : null;
return name == null ? LanguageMenuOrder.label(code) : name;
```

- `nativeLabels` 来自 `CaptionLanguageMetadata` 观察到的 YouTube 元数据标签；有就**原样使用**。
- 没有才走 `LanguageMenuOrder.label(code)`。

`LanguageMenuOrder.label()`（`ui/.../LanguageMenuOrder.java:43-46`）只对 `zh-Hans` 做了
`simplifiedLabel()` 特判；`zh-Hant` 直接落到：

```java
Locale.forLanguageTag(code).getDisplayName(locale())
```

Robolectric（SDK 28/33，中文 UI）实测：

```text
label(zh-Hans)=中文（简体）
label(zh-Hant)=中文 (繁体)
```

注意这里是**半角空格**的 `中文 (繁体)`，不是应用资源里的全角 `中文（繁体）`，更不是
`中文（繁体中文）`。所以：

- 如果扩展插入新条目，`translationLabel("zh-Hant")` 在元数据没有该 code 时给出 `中文 (繁体)`；
- 如果元数据已有该 code，则给出 YouTube 的原生标签（用户看到的 `中文（繁体中文）`）；
- 如果原生列表已有该 code（本次诊断正是如此），`augmentTranslations` 直接保留原生对象，标签完全由 YouTube 决定。

### 2.4 根因归纳

- **R2-1（直接）**：本次“添加”的繁体中文并没有被扩展插入（0 次 `LANGUAGE_MENU_INSERTED`）；它已经是
  YouTube 原生条目，`displayName` 是 YouTube 的“中文（繁体中文）”。
- **R2-2（结构）**：菜单标签没有单一权威。`cap_language_zh_hant` 只用于设置页；YouTube 菜单优先用原生
  `displayName`，其次用 ICU `getDisplayName`，两者都不等于应用资源。
- **R2-3（一致性）**：`LanguageMenuOrder.simplifiedLabel()` 只特判简体，繁体走 ICU，连标点/空格都与应用
  资源不一致；即使不是原生标签，也会出现 `中文 (繁体)` 这种次优形式。

### 2.5 修复方向

1. 为所有目标语种建立**唯一的本地化标签函数**（设置页、元数据、克隆轨、排序都用它），不要优先原生标签。
2. 若产品要求“添加的语种用应用标签”，则对已存在的原生条目也要能替换/覆盖显示名，而不是保留原生对象；
   或者明确接受原生标签并在文档中说明。
3. 给 `zh-Hant` 增加与 `zh-Hans` 对称的 `traditionalLabel()`，统一全角括号和“繁体”措辞；补 14 语言测试。
4. 诊断里记录 `LANGUAGE_MENU_INSERTED` 的 `display_name`/来源（native/icu/resource），目前无法从诊断判断
   标签来自哪个分支。

## 3. 问题三：自动生成字幕为原语言时翻页位置明显不正确

### 3.1 诊断事实：所有源都没有逐词计时

当前文件 22 次 `REBUILD_SOURCE_READY`，**每一次都是**：

```text
measured_or_aligned=0; estimated=<全部词>; coarse_reconstructed=true/false
```

包括自动生成的英文/日文视频。以 `mH5TlcMo_m4`（session 123）为例：

```text
SOURCE_OK Source captions: 158900 bytes
REBUILD_SOURCE_REFERENCE_SKIPPED session=123;native_words=0;words=9684;reason=no_native_word_timing
REBUILD_SOURCE_READY words=9684;measured_or_aligned=0;estimated=9684;
                   coarse_reconstructed=true;coarse_cues=743;blocks=127
```

同一视频的用户提供的 `.en.json3` 是 **1,069,950 B**，用生产解析器得到：

```text
SOURCE mH5.en.json3 words=9684 native=9651 estimated=33 coarse_cues=22
```

也就是说：**同一个视频、同样的 9,684 个词，真实 JSON3 有 9,651 个逐词时间；运行时拿到的 158,900 B 载荷一个都没有。**
这不是分页算法“算得不够好”，而是**计时证据在进入规划器前就丢了**。

### 3.2 证据是怎么丢的：两层

#### 第一层：XML/srv3 的 `<s t>` 被解析后又被丢弃

`CaptionDocument.parseXml()` 会为每个 `<s t="...">` 生成 `RawFragment(nativeOffset=true)`（`CaptionDocument.java:292-323`）。
但 `RebuildSource.read()` 的通用回退分支（`RebuildSource.java:519-523`）只做：

```java
if (spans.isEmpty() && !webVtt) {
    for (CaptionDocument.Cue c : parsed.cues())
        spans.add(new Span(c.text, c.startMs, c.endMs, i++, false));
}
```

它**没有读取 `parsed.rawFragments()`**。于是 XML 里已有的 `<s>` 起点全部被压扁成整条 `<p>` cue，
再在 `addTokens()`（`:780-807`）里按 token 数均分整个 cue 窗口。

离线探针 `TmpXmlTimingProbeTest` 直接复现：

```text
PARSED detected_fmt=xml;raw_fragments=15;offset_segments=15
RAW nativeOffsets=15 fragments=15 cues=2
REBUILD words=15 native=0 coarse_cues=2 anchors=4
  0 before 80-331 ESTIMATED
  ...
  14 people 4499-4880 ESTIMATED
```

`CaptionDocument` 明明解析出 15 个原生 offset，`RebuildSource` 却让 15 个词全部变成 `ESTIMATED`。
运行时 `coarse_cues=743`、`native_words=0` 与这个分支完全吻合；因此运行时载荷很可能是 srv3/XML（或
不带内嵌时间标签的 VTT），而不是用户提供的 JSON3。JSON3 分支 `json3Spans()` 单独读 `tOffsetMs`，不受
这个缺陷影响，这也解释了为什么离线 JSON3 有 9,651 个 native，而运行时是 0。

#### 第二层：`native=0` 反而让 ASR 计时参照被跳过

`RebuildController.load()`（`:994-1012`）：

```java
if (!s.sourceOnly
        && source.nativeWordCount() > 0
        && source.nativeWordCount() < source.words.size())
    source = alignedToReference(s, source, control);
else if (!s.sourceOnly)
    mark("REBUILD_SOURCE_REFERENCE_SKIPPED", "...;reason=no_native_word_timing");
```

这个门槛的语义是“主源已经有一部分逐词时间时，才去取参照补全”。但主源**完全没有**逐词时间时，恰恰最需要
参照；现在却直接跳过。诊断里 18 次 `REBUILD_SOURCE_REFERENCE_SKIPPED` 全是 `native_words=0`，说明
`NativeAsrTrackReference` / `WordTimingReference` 的候选路径从未被尝试。即使 YouTube 另有带词级 offset 的
ASR JSON3，它也不会被取来对齐。

### 3.3 页面时间因此只能“按字数均摊”

`RebuildPageLayout.allocate()`（`:325-349`）与 `CaptionLanguagePager` 的分配逻辑（`:58-85`）都是：

```java
weights[i] = weight(parts.get(i));          // 可见字符 + 标点停顿
long span = Math.max(1, (end - at) * weights[i] / remaining);
```

`end/at` 来自模型事件的起止；模型事件的起止又来自 `RebuildSource` 的估计词时间。于是出现**双重近似**：

1. 粗 cue 窗口内按 token 数均分（`addTokens`）；
2. 页面在事件窗口内按阅读量均分（`allocate`）。

真实语速、停顿、重叠、滚动窗口全部丢失。页面翻页点自然会在几百毫秒到一秒以上的范围内漂移。

### 3.4 一个可核对的错位例子

session 123，`id=123:2:2:98-126`，`page_basis=ESTIMATED_PAGE_TIMING`：

```text
page 1/2  page_range=28920-31043  text=虽然很容易嘲笑这类叙事，
page 2/2  page_range=31043-36925  text=但事实是，此类文章获得了数百万的浏览量和关注，塑造了公众舆论。
```

用户提供的 JSON3 逐词时间：

```text
29760 and / 29920 while / 30080 it's / 30320 easy / 30560 to / 30720 laugh / 30960 at
31119 these / 31279 kind / 31519 of / 31599 narratives
32079 the / 32239 fact / 32480 remains ...
```

- 第 1 页文字包含“这类叙事”，对应 `these kind of narratives`，最后一个词 `narratives` 起于 **31.599 s**；
  但第 1 页在 **31.043 s** 就结束了，提前约 **556 ms**。
- 第 2 页首句“但事实是”对应 `the fact remains`，`the` 起于 **32.079 s**；但第 2 页在 **31.043 s** 就出现，
  提前约 **1.036 s**。

这就是用户看到的“翻页位置显然不正确”：下一页在上一句还没说完时就出现，且它的第一句还没开始说。
同类错位在 `123:2:5:334-364`（第 1 页在 `missiles` 起于 113.040 s 之前于 112.817 s 结束）也存在。

### 3.5 还有一层：页面身份随几何重排改变

同一 `id=123:2:7:527-556`：

```text
fullscreen, available_width_px=2025: page 1/2  165680-170036
detail,     available_width_px=1121: page 1/3  165680-168542
                                      page 2/3  168542-170035
```

同一段译文在全屏/详情切换后从 2 页变成 3 页，`并非因为他们刻意隐瞒，` 从第 1 页尾变成第 2 页首，
时间边界也随之改变。页面边界由**当前几何**决定，而不是由稳定的源语句边界决定；这会让用户在旋转、
全屏、画中画切换时看到翻页位置跳变。它与 3.3 的估算叠加，放大了“位置不对”的感受。

### 3.6 根因归纳

- **R3-1（直接）**：`CaptionDocument` 解析出的 XML `<s t>` 原生片段被 `RebuildSource` 的通用回退分支丢弃；
  JSON3/VTT 分支才有逐词时间。
- **R3-2（直接）**：`RebuildController` 只在 `nativeWordCount() > 0` 时取 ASR 参照；主源为 0 时跳过参照，
  逻辑方向反了。
- **R3-3（结构）**：页面时间在估计事件窗口内按阅读量均摊；页面边界又随几何重排改变。没有“源语句锚点”
  作为稳定翻页依据。
- **R3-4（传输）**：运行时拿到的是 158,900 B 的粗载荷，而不是 1,069,950 B 的 JSON3；格式协商/回退路径
  没有保证“带词级 offset 的格式优先”，也没有在诊断里记录实际 format/track kind。

### 3.7 修复方向

1. 让 `RebuildSource.read()` 统一消费 `CaptionDocument.rawFragments()`（至少 XML 的 `<s t>`），不再只认
   VTT/JSON3 的两种特例；`CaptionDocument` 已有 `nativeOffset` 证据。
2. 把参照门槛改成“主源计时粗糙（`nativeWordCount() < words.size()` 或 `coarseCueReconstructed`）就尝试
   参照”，而不是“必须已有 native 才尝试”。
3. 页面时间优先使用源词/源段锚点；没有锚点时才按阅读量均摊。页面身份应以源 token 范围为主键，几何只决定
   行数，不决定“这是第几页”。
4. 诊断增加 `detected_fmt`、`raw_fragments`、`offset_segments`、`primary_native/native/estimated`，
   让下一次可以直接确认运行时 payload 是 JSON3 还是 srv3。

## 4. 问题四：人工字幕为原语言时翻译质量不佳

### 4.1 请求粒度：400 个 cue = 400 个请求块（通常一次 API 调用）

离线探针用真实 `FzRyrjFmZSQ.ja.vtt` 跑生产 `RebuildPlanner.planAuthored()`：

```text
SOURCE FzRyrjFmZSQ.ja.vtt words=7549 native=0 estimated=7549 coarse_cues=400
manual cues=400
manual blocks(planAuthored)=400
  block b0_0_33 500-5250 cue=0 text=最近、ガジェット業界を世界的にざわつかせた通販サイトをご存じでしょうか
  block b1_34_39 5250-6250 cue=1 text=それがこちら
  block b2_40_41 6750-8167 cue=2 text=「AppleUnsold」
  block b3_42_46 8167-9375 cue=3 text=雑に訳せば
  block b4_47_48 9375-11000 cue=4 text=「Appleの未発売品」
  block b5_49_62 11000-12583 cue=5 text=くらいのニュアンスなんですが
  block b6_63_77 12583-14792 cue=6 text=話題になった理由はいたって単純
  block b7_78_92 14792-17292 cue=7 text=何とこのサイト、その名前の通りに
  block b8_93_105 17292-21208 cue=8 text=「公式に販売されていないApple製品を専門に取り扱う」
  block b9_106_137 21208-25375 cue=9 text=という、どう考えても闇が深すぎるコンセプトで運営されているんですよ
  ...
```

`RebuildGuidance.authoredPrompt()`（`:52-62`）明确要求：

> Return exactly one event per cue, covering that cue's tokens and nothing else; never merge two
> cues into one event and never split one cue across events. Translate each cue so its own text
> reads naturally; neighbouring cues are context only.

`widenContext()`（`:101-113`）会带 600 token 的前后文，但只是 `context_before/context_after`，
**输出仍然被限制在一个 cue 内**。因此：

- `それがこちら` 被当成完整句翻译成“这就是这个”；
- `くらいのニュアンスなんですが` 这种依赖前句的省略句被单独成页；
- `という、...` 开头的句子失去与上一条引文的衔接；
- `しかも` / `しかし` 这类单词 cue 各自成页（诊断中 `10:3:47` = “而且”，`10:3:48` = “然而”）。

这不是“模型不聪明”，而是**请求单元 = 显示单元**的结构限制：模型即使看懂了上下文，也不能把两个 cue
合成一个自然的中文句子，因为输出协议要求一个 cue 一个 event。

### 4.2 更严重：日文源根本没有目标语言校验

`CaptionLanguageContext`（`caption-shared/.../CaptionLanguageContext.java:15-27`）只有：

```java
canApplyEnglishToChinese = englishSource && (target zh-Hans || target zh-Hant);
```

`RebuildSemantics.validate()`（`translation-core/.../RebuildSemantics.java:155-158`）第一行就是：

```java
if (!context.canApplyEnglishToChinese) return;
```

也就是说，**`ja → zh-Hans` 时所有语义、数字、装备锚点和目标语言检查全部跳过**。

诊断质量证据里有一条直接命中：

- request 98，session 10，block `b75_1285_1310`，源文：
  `配送方法は通常とそれより少し速いものと2種類が選べて`
- 模型回复（qwen3.7-flash）：
  `配送方法には、通常とやや高速の2種類を選べます。`
- 这是**日文**，不是中文；`REBUILD_EVENTS_ACCEPTED block=75;events=1`，没有拒绝，最终页面
  `10:3:75` 就显示这段日文。

同样，session 10 的 `国内和海外都还没有怎么上涨。` 把“报告几乎还没出现”误译成“上涨”，也没有任何
语义检查拦截（`canApplyEnglishToChinese=false`）。

这说明“人工字幕质量不佳”至少有两层是**代码可解释的**：

1. 请求形状把句子切碎，模型只能逐 cue 产出；
2. 目标语言/语义校验只覆盖英译中，日译中即使原样返回日文也会被接受。

### 4.3 人工 cue 的严格引文校验还会造成整块丢弃

同一诊断 `1792389150985`：

```text
REBUILD_EVENTS_REJECTED block=22;reason=source_quote_mismatch;session=10;request=43;
exact source=世界的話題の闇通販サイト「AppleUnsold」の実態に迫っていきます
```

人工 cue 的 `source` 必须与源文逐可见字符相等（`RebuildProtocol.sameSource()`，`:546-559`）。模型若把
`「」` 改成 `“”`、或把 `AppleUnsold` 前后空格处理得不同，整条 cue 的译文会被丢弃并重试。对人工字幕，
一条 cue 往往就是一句话；一次引文格式差异就会造成该句空白或延迟。它不是“质量差”的主因，但会放大
“缺句/闪空”的体感，且与“逐 cue 请求”叠加。

### 4.4 根因归纳

- **R4-1（结构）**：人工源的请求块 = 源 cue（`planAuthored`），不是句子/段落；`CUE` 指令又禁止合并 cue。
  半句、单词 cue 只能被译成半句/单词页。
- **R4-2（校验）**：语义/目标语言校验被 `canApplyEnglishToChinese` 门禁限制；非英译中完全不校验，日文
  原样返回也会被接受。
- **R4-3（引文）**：人工 cue 的 exact-quote 校验对全角/半角标点、引号差异零容忍，容易整块丢弃。
- **R4-4（模型）**：以上是代码结构原因；模型本身在长句/文化语境上的能力仍是残余变量，不能用 prompt
  补丁替代结构修复。

### 4.5 修复方向

1. 把**翻译单元**从显示 cue 中解耦：以相邻 cue 组成的完整句/段为请求块，返回事件带源 token 范围；
   显示层再按 cue/子句分页。cue 只作为显示边界，不作为请求边界。
2. 对**所有** source→target 组合做目标文字/语言校验（至少：目标为中文时禁止假名/谚文；目标为英文时
   禁止 CJK 占比过高；源文回声检测），而不是只对 en→zh 生效。
3. 引文校验对人工 cue 允许标点归一（全角/半角、引号样式），或改用 token 范围 + 可见字符序列的宽松匹配；
   不要把整块译文因一个引号丢弃。
4. 增加诊断：`request_block_kind=authored_cue|sentence`、`target_script_check=pass|fail`、
   `source_echo_ratio`、`cue_merge_count`。

## 5. 四项问题的共同结构

把四条根因放在一起，会看到同一个模式：

| 层 | 现在的事实 | 后果 |
|---|---|---|
| 用户意图 | `CaptionChoice` 被原生默认覆盖；记忆只在默认选择器里被查询 | 语种回到简体 |
| 轨道身份 | 克隆轨 `language=zh-Hans`；标签有原生/ICU/资源三套 | 记忆和标签都错位 |
| 计时证据 | XML `<s t>` 已解析但被丢弃；native=0 时反而不取参照 | 翻页漂移 |
| 翻译单元 | 请求块 = 源 cue；校验只覆盖 en→zh | 人工字幕半句化、日文回声被接受 |

它们不是四个独立 bug，而是**没有单一权威模型**：

- 语种没有单一权威（native default / CaptionChoice / Remembered / handoff 四套）；
- 轨道身份没有单一权威（`language` 字段 / `tlang` / `displayName` / vss 四套）；
- 计时没有单一权威（`CaptionDocument` 的 rawFragments / `RebuildSource` 的 VTT/JSON3 特例 / 估计时间三套）；
- 翻译单元没有单一权威（cue / 模型 event / 页面 / 几何行四套）。

因此“在错误基础上打补丁”的典型做法——改标签字符串、强制 zh-Hans、调分页阈值、再加一段 prompt——
都只能改变症状的形态，不能消除权威冲突。正确的方向是：

1. **一个选择状态机**：显式用户选择 > 记忆 > 原生默认；自动默认永远不能覆盖显式选择。
2. **一个轨道身份**：`targetCode` 是唯一身份，`displayName` 只是本地化表现；克隆/插入都必须保留 code。
3. **一个计时证据模型**：所有格式的 native offset 进入同一 `SourceTiming`，粗计时才走参照/估计。
4. **一个翻译单元模型**：句子/段落请求，cue/页面只是显示投影；目标语言校验与源语言无关地执行。
