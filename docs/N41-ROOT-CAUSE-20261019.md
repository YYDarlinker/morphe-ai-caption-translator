## 0. 一句话结论

人工源翻页不是“分页器算得不够好”，而是**人工 cue 的显示契约从来没有进入实现链路**：
`RebuildGuidance` 里已经写好的 cue 规则、cue 范围、`reviewCues()` 和 600-token 上下文
**全部没有调用者**；真正上屏的 `authoredUnits()` 是“一个模型 event 一个显示单元”，而不是
“一个 cue 一个显示单元”。因此模型把 cue 切成几个 event，就变成几页；模型把几个 cue 合
成一个 event，就由 `shareOut()` 按源文字符比例硬切译文。诊断中的 10 个 cue 被拆成 2–4 页、
22/44 个页窗不落在 cue 边界、`，` 单独闪 390 ms、块 7 连续 13.875 s 无译文，都是这一条
结构性断链的出口，而不是四个独立 bug。

## 1. 设计要求与实际链路

设计要求（用户本轮明确）：

1. 人工源与自动源使用**同一套译文质量把控逻辑**；
2. 人工源的字幕翻页**完全按照人工 cue**；译文在同样的位置对应到同样的 cue；
3. 不允许在错误的基础上打补丁。

实际链路：

| 层 | 人工源（`authored=true`） | 自动源（`authored=false`） |
|---|---|---|
| 请求块 | `RebuildPlanner.planAuthored()`，4 cue/600 字符/20 s | `RebuildPlanner.plan()`，句子/资源块 |
| 请求提示词 | `RebuildApi.prompt()` 只追加 `SENTENCE`；**没有 cue 规则、没有 cue 列表** | 同一 `SENTENCE` |
| 请求上下文 | `payload()` 只带 24 token 前后文；`widenContext()` 的 600 token **未调用** | 24 token |
| 解析/校验 | `parseBound()` 只校验 token 范围、quote、目标文字；**没有“一 cue 一 event”校验** | 同一 `parseBound()` |
| 质量 review | `RebuildReview.inspect()` 对 `ja→zh` 几乎没有有效门禁 | 同一 `inspect()`，但 `en→zh` 专属检查生效 |
| 显示单元 | `authoredUnits()`：**一个 event 一个 Unit** | `RebuildDisplayGroups.partition()`：合并、hold、可读性检查 |
| 分页 | `RebuildPageLayout`：event 文本；`spec.authored` 只放宽到两行 | 同一分页器 |
| 失败/空白 | 块未接受时显示 `翻译中…`；块 7 13.875 s 无译文 | 计划就绪但无页时空白 |

这条链路里，人工 cue 只出现在 `planAuthored()` 的块规划里；**从请求、校验、缓存到显示，
cue 边界都没有作为一个必须满足的契约继续传递**。代码里唯一明确写“pages follow the
author”的地方是 `CaptionRenderSpec` 的注释（`CaptionRenderSpec.java:29-30`），但字段
`authored` 的唯一使用点是 `RebuildPageLayout.unitPages()` 的“允许两行”
（`RebuildPageLayout.java:188`）。注释描述的契约没有实现。

全屏/详情宽度都可能放进两行；但它是 4 个独立页帧，每页 `page=1/1`、`page_basis=SOURCE_EVENT`。
`page=1/1` 说明它不是 `RebuildPageLayout` 在一次显示单元内切出来的 1/2、2/2，而是四个

“一个 event 一个 Unit”在这里没有任何遮挡空间。

### 2.2 直接代码原因：`authoredUnits()` 是“一 event 一页”

`RebuildController.java:1788-1813` 的注释写的是：

> One display unit per manually authored cue. The model may split or join its own events inside
> the cue, but the page the viewer sees is the cue the author wrote.

实现却是：

```java
for (RebuildProtocol.Event event : plan.events) {
    List<int[]> cues = cueSpans(s, event);
    if (cues.size() <= 1) {
        units.add(newUnit(index, event, event.text, event.end));
        continue;
    }
    List<String> parts = shareOut(event.text, cues, s);
    ...
}
```

- `cues.size() <= 1` 时，**直接把 event 当成 Unit**；如果同一 cue 有 4 个 event，就产生 4 个
  Unit。cue 20 正是这条路径。
- 只有 event **跨了多个 cue** 时才走 `shareOut()`；它按“每个 cue 的源文字符数”比例切译文
  （`RebuildController.java:1835-1861`），再用 `nearestClauseMark()` 在附近找标点/词边界。
  这是**按字符比例伪造 cue 边界**，不是把译文语义对齐到 cue；切出来的文字可能刚好落在
  某个词中间，也可能把上一 cue 的谓语留在下一 cue 的页。
- `newUnit()`（`RebuildController.java:1815-1819`）把 `end` 设为 `event.end`；对于只覆盖
  cue 一部分的 event，页窗就是该 event 的估计词时间，而不是 cue 时间。于是出现
  `21,208–21,598` 这种“390 ms 的 `，` 页”——这个时间不是作者 cue 的时间，是把 cue 的
  估计词时间按 token 均分后得到的虚构边界。

**结论：`authoredUnits()` 的契约与实现相反。** 它不能保证“一个 cue 一个 Unit”，最多只能
保证“一个 Unit 不跨多个 cue 的源文字符比例”。这不是分页器阈值问题。

### 2.3 校验层：`reviewCues()` 没有调用，而且它本身也查不出 split

`RebuildGuidance.reviewCues()`（`RebuildGuidance.java:69-91`）本意是“每个 event 必须落在
一个 cue 内”，实现只做：

```java
int first = source.words.get(event.from).cue, last = source.words.get(event.to).cue;
if (first == last) continue;
issues.add(new Issue(..., "cue_boundary", ...));
```

它只能发现 **event 跨 cue（merge）**，发现不了 **一个 cue 里有多个 event（split）**。即使
把它接上，cue 9 的 `106-108 / 109-137`、cue 20 的四段仍然全部 `first == last`，仍然 0 个
issue。

更关键的是：**它根本没有调用者。** 全仓库检索 `reviewCues`、`authoredPrompt`、
`cueDirective`、`widenContext` 只有定义，没有调用：

- `RebuildGuidance.authoredPrompt()`（`:52-62`）——未调用；
- `RebuildGuidance.cueDirective()`（`:16-27`）——未调用；
- `RebuildGuidance.reviewCues()`（`:69-91`）——未调用；
- `RebuildGuidance.widenContext()`（`:101-113`）——未调用。

即使把 `reviewCues()` 接上，它也只会给 `cue_boundary` 增加一个 `repair` issue；而
`RebuildController.translate()` 在 `shouldRepair()` 之前就把 `accepted` 写入 `s.plans`
（`RebuildController.java:1554-1562`）。`render()` 下一次 tick 就会显示这个计划，repair 只是
后台再来一次。也就是说，cue 契约不是**准入条件**，而是事后建议；这仍然会先把错误分页
上屏。人工 cue 的 1:1 关系必须作为 admission gate（不满足就不发布），不能只做 advisory。

缓存层同样没有 cue 契约：`RebuildCache.identity()` 只哈希 `start/end/precision/text`
（`RebuildCache.java:41-65`），不哈希 `Word.cue` 或 authoredness；`RebuildCache.read()`
只调用 `parseBound()`（`:84-103`），不调用任何 cue 校验。即使解析层以后加了
“一 cue 一 event”，命中旧缓存仍可绕过；修复时必须把显示契约纳入缓存 identity，并在
`read()` 重新验证。

探针用生产 `RebuildApi.prompt()` 打印实际请求提示词：

```text
PROMPT_SENT has_authored_rule=false;has_cue_list=false;has_cue_directive=false
PROMPT_INTENDED has_authored_rule=true;has_cue_list=true;has_cue_directive=true
```

`RebuildApi.prompt()`（`RebuildApi.java:119-127`、`:154-165`）永远只追加
`RebuildGuidance.SENTENCE`；`RebuildApi.translate()` 的签名（`:167-176`）里甚至没有
`authored` 参数，`RebuildController.translate()` 调用它时（`RebuildController.java:1492-1500`）
也只传 `s.source,b,...`。**人工/自动的区分在进入翻译 API 之前就丢了**，所以 request 层
没有能力知道“这是人工源”，也就无法应用 cue 规则。

### 2.4 显示层：人工路径绕过了成熟的 `RebuildDisplayGroups`

自动源的显示单元由 `RebuildDisplayGroups.partition()` 生成（`RebuildDisplayGroups.java:78-167`）：

- 合并短事件，避免一个词/一个引子单独成页；
- `HOLD_MS` 内把 Unit 的 `end` 延伸到下一句开始，避免 cue 间小空隙闪空
  （`:154-157`）；
- `readable()` 检查两行、阅读速率和时长（`:318-337`）；
- `lead`/`tail`/`pageCost` 把“另一方面，”“因此，”这类引子与后半句放在一起
  （`:104-118`、`:212-217`）。

人工源在 `displayUnits()` 里直接 `return authoredUnits(...)`（`RebuildController.java:1994`），
**完全绕过这套逻辑**。探针把 cue 15 的两个 event 喂给生产 `RebuildDisplayGroups.partition()`：

```text
GROUP_LEAD_CUE15 events=2;authored_units=2;partition_units=1;
text=另一方面，关于在该网站实际购物的报告
```

也就是说：**现有的自动显示合并逻辑本来可以把这个引子页合掉；人工路径没有用它。**
这不是“人工源需要特殊逻辑”，而是人工路径被实现成了另一条更简陋的平行管线。

同时，`authoredUnits()` 不延长 `HOLD_MS`，所以 cue 间的小空隙不会被 Unit 本身覆盖。覆盖层
`CaptionOverlayV2.holdingEnd()` 会在最后一页结束后最多保持 `END_HOLD_MS=800 ms`
（`CaptionOverlayV2.java:733-751`），因此 500 ms 的 cue 间隙（cue 1 结束 6,250、cue 2 开始
6,750）通常不会闪空；但 1,000 ms 的间隙（cue 22 结束 70,792、cue 23 开始 71,792）会留下
约 200 ms 空白。自动源 `RebuildDisplayGroups.partition()` 用 `HOLD_MS=1000` 把 Unit.end
延伸到下一句开始（`RebuildDisplayGroups.java:154-157`），人工路径没有这层一致性。这是
次要问题，不是本轮翻页错误的主因，但它说明人工路径确实绕过了自动路径的显示质量逻辑。

### 2.5 分页器：即使一 cue 一 event，也仍可能被切成多页

`RebuildPageLayout.unitPages()`（`RebuildPageLayout.java:177-206`）的第一步是：

```java
if (fitsOne.test(text) || spec.authored && fitsTwo.test(text))
    return Collections.singletonList(new Page(text, start, end, "SOURCE_EVENT"));
```

`spec.authored` 只把“一行”放宽到“两行”；如果译文超过两行，仍会走 `pageCuts()` + `pack()`
按标点切成多页。探针用一个人工 spec 和一个单 cue 的四分句文本：

```text
SINGLE_CUE_SYNTHETIC pages=2 [58750-61003 甲乙丙，丁戊己，][61003-63708 庚辛壬，癸子丑。]
```

也就是说，**“一 cue 一页”在分页器里也不是不变量**。当前覆盖层 `CaptionOverlayV2` 还把
`maxLines` 固定为 2（`:1267-1270`），所以一个 cue 的译文一旦超过两行，只有两种结果：
被分页器切成多页（违反 cue 翻页），或者退回 `fullPage()` 后被 TextView 截断（丢文字）。
这是“cue 原子性”和“固定两行”之间的设计冲突，必须显式决定 overflow 策略；不能在分页器里
偷偷切。

此外，`unitPages()` 的单页分支（`:188`）不检查 `MIN_PAGE_MS`。诊断中的 `，` 页 390 ms、
`另一方面，` 页 425 ms 都能通过；`plan()` 先调用 `unitPages()`（`:94-95`），单页直接返回，
`preferredLegacyPlan()` 里的 `duration < MIN_PAGE_MS` 保护（`:42-45`）根本轮不到。短页
闪烁是这条路径的直接结果，而不是“模型返回太快”。

### 2.6 根因分层

**L1 直接原因（观测层）：** 模型把 cue 切成多个 event；`authoredUnits()` 把每个 event 当页；
`shareOut()` 对跨 cue event 按字符比例切译文；分页器只放宽两行，不保证 cue 原子性。

**L2 结构原因（契约层）：** “人工/自动”只是 session/URL 上的一个布尔值，没有作为
**显示契约**进入 `Block`/`Plan`/request/cache。请求 API 拿不到它，校验层拿不到它，显示层
只能靠 `authored(s)` 再猜一次。cue 范围、cue 数量、cue 与 event 的对应关系没有数据结构承载，
所以任何一层都无法验证“这一页是不是这个 cue”。

**L3 设计原因（权威层）：** 翻译单元（sentence/block，质量）和显示单元（cue，翻页）被
混成同一个东西。N40 试图用“一个 cue 一个 event”把两者绑在一起，但既没有把规则接到请求，
也没有把校验接到解析；显示层又退化成“一个 event 一页”。正确的关系应该是：
**翻译仍按句子/块做质量把控；显示时把译文投影到固定 cue 边界**（或至少把 cue 作为硬约束
在解析后验证、不满足就不发布）。现在两头都没有落地。

**L4 过程原因（验证层）：** N40 关于人工源分页的回归只测了 `planAuthored()` 把 3 个 cue
分成 1 个 block（`N40RegressionTest.authoredBlocksGroupCuesWithoutCrossingASentence`），
没有测：
- authored request 是否真的包含 cue 规则；
- `parseBound()` 是否拒绝“一 cue 多 event”；
- `authoredUnits()` 的 Unit 数是否等于 cue 数；
- 页窗是否等于 cue 窗；
- `reviewCues()` 是否被调用。

死代码能编译、测试能通过，文档却写“reviewCues 继续拒绝跨 cue event”，这就是本轮问题
没有被上一轮验证发现的原因。N40 修复文档第 4.1 节的这句话与当前源码不符，应视为文档
证据，而不是实现证据。

## 3. 问题二：“同一套质量把控逻辑”实际没有生效

### 3.1 请求块不同、上下文更窄、校验更少

人工源 `planAuthored()` 的块是 4 cue/600 字符/20 s（`RebuildPlanner.java:47-80`），自动源
`plan()` 是 160 词/1600 字符/30 s（`:16-17`、`:82-135`）。人工源的块更小，本身不是错；
但它带来两个后果：

1. **质量 review 的统计口径随块变化**。`RebuildReview.inspect()` 的 `words`、`han`、
   `fragmented_plan` 等阈值都按块内事件计算；人工块只有 4 cue，模型更容易把每 cue 切成
   短 event，`fragmented_plan` 反而更少触发。
2. **上下文更窄**。`payload()` 只给 24 token 前后文（`RebuildProtocol.java:217-218`）；
   `RebuildGuidance.widenContext()` 的 600 token 没有调用。人工 cue 常是半句，24 token
   不足以稳定消歧。

### 3.2 `ja → zh-Hans` 的质量门禁基本为空

`RebuildReview.inspect()` 里大量检查以 `english && zh` 或
`context.canApplyEnglishToChinese` 为条件（`RebuildReview.java:48-275`）。`CaptionLanguageContext`
只有 `englishSource && target in {zh-Hans,zh-Hant}` 才把 `canApplyEnglishToChinese` 设为
true（`CaptionLanguageContext.java:24-26`）。于是 `ja → zh-Hans`：

- `RebuildSemantics.validate()` 第一行 `if (!context.canApplyEnglishToChinese) return;`
  （`RebuildSemantics.java:238-241`）——整段语义/数字检查直接跳过；
- `RebuildPlanner.dependentEnding()` / `protectedCut()` 也返回 false
  （`RebuildPlanner.java:311-328`），因此“`…の` / `…的` 后面还有名词”这类依赖边界没有
  任何保护；
- `RebuildReview.inspect()` 的 `possible_omission`、`possible_relation_omission`、
  `dependent_boundary`、`invented_sentence_end` 等都不会触发。

探针直接调用生产代码：

```text
REVIEW_JA_CUE9 issues=0;REVIEW_JA_CUE15 issues=0
SEMANTIC_VALIDATE_JA_ZH accepted_without_error=true
```

也就是说，对 `ja→zh`，**故意写错整句译文也不会被 `RebuildSemantics.validate()` 拒绝**。
这不是“模型偶尔译错”，而是“这一语言对没有质量门禁”。

诊断里的具体后果：

- cue 18 的页 1 以 `…众多黑幕的` 结尾，页 2 才出现 `我们家的投稿者，`——把“的”前面的
  修饰语和中心词拆到两页；
- cue 22 的页 1 以 `…“AppleUnsold”的` 结尾，页 2 才是 `真实情况。`——同一个名词短语
  被拆开；
- cue 7 的页 1 `这个网站竟然，`、页 2 `正如其名。`——引子被单独成页；
- cue 9 的 `，` 页——一个标点单独成页；
- 块 7 的 `その点をあらかじめ強調したところで改め`（token 562–580）在词中结束，随后
  `source_quote_mismatch` 三次，整块 13.875 s 没有译文。

诊断的 `REBUILD_EVENTS_ACCEPTED block=5;events=7;session=13;review_risks=0` 是同一问题的
量化证据：3 个 cue 产生 7 个 event，质量 review 仍然给 0 个风险。也就是说，当前 review
根本不把“event 数不等于 cue 数”视为问题。

### 3.3 精确引文门禁把“格式差异”当成“翻译失败”

`parseInternal()` 对每个 event 要求 `source` 与 `s.text(from,to)` 的可见字符完全相等
（`RebuildProtocol.java:354-368`）；`sameSource()` 只忽略空白（`:547-549`）。不匹配时
`alignBySource()` 要求所有 quote 按顺序覆盖整个块，首 quote 必须从块首开始，quote 之间
最多 4 个字符空洞（`:482-537`）。任何一次标点/引号/词中边界差异都可能让整块失败。

块 7 的证据：

```text
block=7;reason=source_quote_mismatch; range=562-580;
exact source=その点をあらかじめ強調したところで改め
```

`改め` 是 `改めて` 的词干；`from/to` 落在词中，说明模型选择的事件边界不是日语词边界。
`reviewCues()` 即使被调用也只看 cue 编号，不看词边界；`RebuildReview` 的
`dependent_boundary` 只对 `canApplyEnglishToChinese` 生效。于是：

1. 模型的 `to` 落在词中；
2. `source` quote 与 `s.text(562,580)` 不等；
3. `alignBySource()` 无法在“所有 quote 覆盖整块”的约束下恢复；
4. 三次 repair 后块 7 没有 accepted plan；
5. `render()` 只能按 cue 显示 `翻译中…`，13.875 s 无译文。

这是**质量门禁的可用性失败**：它把“模型复制引文时的格式差异/词中边界”当成了“译文质量
不合格”，整块丢弃，而不是只重试该 cue 或用 token 范围作为权威。对人工源，块越大，单次
quote 差异的爆炸半径越大（块 7 覆盖 4 个 cue）。

### 3.4 目标文字校验只查“有没有汉字”，不查“有没有残留源文”

`RebuildSemantics.validateTarget()` 对中文目标只要求“有汉字、没有假名/谚文”（`:175-182`）。
诊断 session 53 的页：

```text
53:1:1:53-72 page=1/2 text=presumably这些人大概认为军事实力的最终裁判标准​
```

`presumably` 是英文源词，整句仍有汉字，所以通过。这不是分页问题，但属于同一类“质量门禁
只做脚本存在性检查”的缺陷：它不能发现残留源词、混排、或目标语句不完整。

## 4. 问题三：自动源的计时证据仍然丢失

### 4.1 诊断与本地文件的直接对照

运行时：

```text
words=9684;measured_or_aligned=0;estimated=9684;coarse_reconstructed=true;
coarse_cues=743;blocks=127;precision=native=0;estimated=9684;aligned=0;
segment_anchors=0;cue_anchors=1486
```

同一视频、同样的 9,684 个词，本地文件用生产解析器：

```text
SOURCE_EN_JSON3 words=9684;native=9651;coarse=22;format=
SOURCE_EN_VTT  words=9684;native=8178;coarse=1495;format=vtt_carry_lines=1482;...
```

本地 JSON3 有 9,651 个逐词时间，本地 VTT 有 8,178 个；运行时是 0。这不是“模型/分页器
算得不准”，而是**计时证据在进入规划器前就没了**。

顺带说明：人工 session 13 的 `precision` 也没有 `vtt_*` 字段，而本地 `.ja.vtt` 用生产
解析器会打印 `vtt_carry_lines=0;...`。这说明运行时的 65,897 B 人工载荷同样不是 VTT 分支
（更像 400 cue 的 JSON3/SRT）；用户提供的 `.ja.vtt` 只用于离线核对 cue 窗口，不能假设
运行时 payload 就是该文件。两个 session 都受“JSON3/SRT 不写 formatEvidence”的影响。

### 4.2 证据是怎么丢的

1. `RawCaptionSource.load()` 在翻译时请求 `SourceFormatPolicy.json3(original)`
   （`RawCaptionSource.java:85-105`）。它只在**解析抛异常**时回退原格式
   （`:95-103`，`SourceRecoveryPolicy.formatFallback()` 只覆盖 `source_format`/
   `source_empty`/`http_400/403/404` 等），**不会因为“解析成功但没有 `tOffsetMs`”而重试**。
2. `RebuildSource.read()` 对 JSON3 走 `json3Spans()`（`RebuildSource.java:662-713`）。
   `json3Spans()` 只有 `segs` 里存在 `tOffsetMs` 才产生带 offset 的 span；没有 offset 时
   每个 event 只产生一个粗 span。`collapseDoubledCues()` 再把滚动重复的 event 折叠；743 个
   粗 span 与“约 1,484 个非空 event 折叠一半”的量级吻合，也与缓存中的 158,900 B 载荷吻合。
3. `formatEvidence` 只在 VTT 分支（`:509`）和 XML 分支（`:545`）设置；JSON3/SRT 分支
   不设置。于是 `precisionEvidence()`（`:313-330`）打印不出 `detected_fmt`，诊断里
   `native=0` 的载荷到底是 JSON3、SRT 还是别的格式，无法从诊断判断。
4. 运行时该会话是 `SOURCE_CACHE_HIT Reused source caption cache: 158900 bytes`
   （`SOURCE_STARTUP_STAGE ... from_cache=true`），说明这次没有重新协商格式；源缓存
   `SourceCaptionCache` 只按 URL/格式/有效期存 body（`:61-106`、`:139`），**不记录
   native word count / timing quality**，粗载荷可以继续命中。
5. 随后 `RebuildController.load()` 在 `nativeWordCount() < words.size()` 时调用
   `alignedToReference()`（`RebuildController.java:999-1003`）。`RawCaptionSource.reference()`
   的唯一入口是 `NativeAsrTrackReference.candidates()`（`:113-182`）；候选列表为空时直接
   `attempts=0`。它确实会对候选 descriptor 调用 `SourceFormatPolicy.referenceProfiles()`，
   理论上可以尝试同一 track 的 srv3/VTT 变体；但前提是 native 菜单曾把该 ASR descriptor
   记入 `NativeAsrTrackReference`（`vss` 以 `a.` 开头）。`attempts=0` 说明候选列表为空，
   或候选都在语言/同 URL 过滤中被跳过；仅凭诊断无法区分。主源 `load()` 自己也没有
   “解析成功但 native=0 就换同 track 格式”的回退。实际效果是：**没有候选时，连一次同 track
   srv3 尝试都不会发生**。诊断只有：

   ```text
   ASR_REFERENCE_UNAVAILABLE attempts=0;reason=no_usable_timing
   ```

### 4.3 后果

- session 53 的 12 个页帧是 `page_basis=ESTIMATED_PAGE_TIMING`；页窗按阅读权重/估计词时间
  均摊，不是真实语音边界。
- `53:1:3:211-236` 的页 1 以 `…如此之少，那么` 结尾，页 2 才 `所有这些…`；页 1 末尾的
  `那么` 是零宽连接后的切点，不是句子边界。源事件 218–228 本身也在 `where are` 处结束，
  模型把一个疑问句切成两半；分页器只是忠实跟随了这个坏事件边界。用本地 JSON3 的真实
  词时间对照（只作同一视频的计时参照）：`well` 69,680、`then` 70,000、`where` 70,159、
  `are` 70,400、`all` 70,560、`these` 70,720；运行时页 2 从 **70,180** 开始，比 `are`
  早约 220 ms、比 `all` 早约 380 ms。页 2 的文字是 `所有这些…`，但它出现时 `all these`
  还没被说出来；页 1 的文字包含 `那么`，但页 1 在 `are` 之前就结束了。这是“下一页在上一
  句还没说完时出现、下一句还没开始”的直接例子。
- 同一 event `53:1:0:0-14`（80–3,600 ms）在 2025 px 下是 1 页，在 1121 px 下是
  2 页（80–1,253 / 1,253–3,600）。页数、页窗随几何变化；这不是“翻页时间不准”，而是
  **页身份本身由几何决定**。

### 4.4 根因

- **能力假设**：代码假设“请求 `fmt=json3` 就会得到逐词 offset”；没有在解析后验证
  `nativeWordCount()`，也没有把“粗载荷”当作可重试的格式问题。
- **格式身份**：`CaptionDocument` 知道 `format`，但 `RebuildSource` 只对 VTT/XML 记录；
  JSON3/SRT 的格式能力被丢掉，诊断无法取证。
- **同一 track 的格式回退没有保证**：`reference()` 有 `referenceProfiles()` 的 srv3/VTT
  变体能力，但只在 `NativeAsrTrackReference` 已有候选 descriptor 时才会被调用；主源
  `load()` 没有“native=0 就换同 track 格式”的路径。候选为空时 `attempts=0`，一次尝试
  也不会发生。
- **缓存没有质量层**：粗载荷命中后不会升级；24 h 内可能一直复用。
- **计时证据没有单一模型**：`parsed.rawFragments()`、`json3Spans()`、`parsed.cues()` 三条
  路径各自决定“什么是时间”，没有统一成 `SourceTiming` 能力对象。

## 5. 问题四：页边界仍由模型事件、零宽连接和几何决定

### 5.1 零宽连接被当成合法页切点

`RebuildDisplayGroups.separator()` 在中文/日文事件之间插入 U+200B
（`RebuildDisplayGroups.java:369-383`），`RebuildPageLayout.pageCuts()` 把 U+200B 当作
切点（`RebuildPageLayout.java:212-231`）。`pack()` 只在页尾是“冒号或短逗号引子”时回退
（`:269-276`、`:287-293`），`那么` 这种没有逗号的连接词不在保护范围。于是
`53:1:3:211-236` 的页 1 可以停在 `那么`，页 2 从 `所有这些` 开始。这不是“零宽字符显示
问题”，是**把模型事件边界当成了语义边界**。

### 5.2 页短于最小显示时间

`RebuildPageLayout.unitPages()` 的单页分支（`:188-189`）和 `allocate()` 的
`parts.size()==1` 分支（`:373-374`）都直接返回 `SOURCE_EVENT`，不检查
`MIN_PAGE_MS`。诊断中的 `，` 页 390 ms、`另一方面，` 页 425 ms 就是这样上屏的。
`CaptionLanguagePager.choose()` 有 `MIN_PAGE_MS` 容量约束，但它只在“多页搜索”里生效；
单页路径绕过了它。诊断侧也没有把这一点暴露出来：`REBUILD_PRESENTATION` 只打印
`page_duration_above_recommendation`（超过上限）和恒为 false 的 `hard_reject`，没有
“低于 `minimum_page_wall_ms`”的布尔值；390 ms 的页在诊断里看起来完全正常。

### 5.3 页身份/页窗随几何变化

`TranslationPresentation.pages()` 每次按当前 `CaptionPresentationBudget` 重新调用
`RebuildPageLayout.plan()`（`TranslationPresentation.java:18-65`）；`CaptionOverlayV2`
的页缓存 key 也把宽度/字号/anchors 算进去（`:767-813`）。所以旋转/全屏/详情切换会重新
分页，页数和页窗变化。对自动源，这也许是可接受的“重排”；但它和“稳定的翻页位置”目标
冲突，且会放大“翻页不对”的体感。对人工源，如果 cue 是页，页身份本应只由 cue 决定，
几何只应影响换行，不应影响页数。

## 6. 共同根因

把上面四条放在一起，会看到同一个模式：

| 权威 | 现在的事实 | 后果 |
|---|---|---|
| 人工/自动身份 | `SourceTrackPolicy.authored(url)` 的 catalog 查询；`machineMade(url)` 的 `kind=asr` 查询；两套定义 | catalog 缺失/URL 变化时人工源静默按自动分页 |
| 翻译单元 | `planAuthored()` 的 4-cue block；请求仍是 `SENTENCE` | 人工源没有 cue 约束，模型自由切 |
| 显示单元 | `authoredUnits()` 的 event；`RebuildDisplayGroups.partition()` 的自动路径 | 两条显示管线，人工路径更简陋 |
| 页边界 | 模型 event、U+200B、几何测量 | cue 边界、语义边界、最小页时长都不稳定 |
| 计时证据 | `json3Spans`/VTT/XML/cue fallback 各自为政；格式化证据缺失 | 自动源 native=0，页窗靠估计 |
| 质量门禁 | `canApplyEnglishToChinese` 门禁；quote 精确匹配；block 级 | ja→zh 近乎无检查；quote 差异整块丢弃 |

更根本地说：**没有“一个 cue 的显示契约”这个单一权威。** cue 是人工作者写的显示边界，
它必须在请求、解析、缓存、显示四层都是不可变的；现在它只是 `planAuthored()` 用来切块的
一个提示，后面每层都可以重新解释它。N40 试图用 `CUE` 提示词和 `reviewCues()` 把 cue
塞进模型事件，但这两段代码没有接线；即使接上，`reviewCues()` 也只查 merge 不查 split，
`authoredUnits()` 仍然按 event 出页。因此这不是“某个阈值不对”，而是**契约没有建模**。

## 7. 根修方向（已按此实施）

以下按“先契约、后实现”的顺序，均是结构性修改，不是调阈值。实施记录见
`docs/N41-REPAIR-20261019.md`。

1. **建立 `DisplayContract`（或 `UnitContract`）**
   - `Block`/`Plan` 增加 `kind = SENTENCE | AUTHORED_CUE`；
   - authored block 携带 cue 列表：`cueId`、`from/to token`、`start/end`；
   - request payload、`Plan`、`RebuildCache` key、诊断都携带同一份 cue 列表；
   - `authored` 不再靠 URL 二次查询；以解析出的 track kind + cue 列表为准。

2. **翻译质量逻辑保持同一套，cue 只做显示约束**
   - 不把 `SENTENCE` 替换成 `CUE` 来改变翻译单元；人工/自动仍用同一套 semantic/numeric/
     target 检查；
   - cue 列表作为请求里的“显示边界”数据，要求模型不要跨 cue 合并；但允许模型在一个 cue
     内给出多个语义事件（用于质量），显示层再合并回 cue；
   - 如果模型跨 cue 合并，解析层必须**拒绝并重试**，不能由 `shareOut()` 按字符比例切。

3. **解析后硬校验（fail closed，不发布违规计划）**
   - 每个 cue 恰好一个显示单元；每个 event 只能属于一个 cue；
   - 每个 cue 的 event 必须覆盖该 cue 的全部 token，不能有 cue 空洞；
   - cue 数 == 页数；页窗 == cue 窗；
   - 违反时走结构 repair；repair 失败则该 cue 显示“翻译中/失败”占位，不能把错误分页
     先上屏再修。
   - `reviewCues()` 应改为“按 cue 聚合 event”，而不是只查 `first == last`；并且必须在
     `RebuildController.translate()` 和 `RebuildCache.read()` 两条路径都调用。

4. **人工显示走 cue 页**
   - 删除 `authoredUnits()` 的 event 循环，改为按 cue 构建 Unit；
   - 同一 cue 的多个 event 合并文本（用同一套分隔符规则，不重复、不丢字）；
   - 跨 cue 的 event 一律拒绝/重试，不用 `shareOut()`；
   - Unit 的 `start/end` 直接取 cue 的 `start/end`，不取估计词时间；
   - 复用 `RebuildDisplayGroups` 的 hold/readability/lead 逻辑，但 cue 边界是硬约束：
     不能跨 cue 合并，不能把 cue 拆成多页。

5. **cue 原子性与两行显示冲突的显式策略**
   - 一个 cue 的译文超过两行时，不能偷偷切成多页；三选一必须在产品层明确：
     (a) authored cue 允许更小字号/更多行；(b) 允许超过两行的 cue 以完整文本上屏并由
     overlay 适配；(c) 明确标记为 overflow 并按 cue 内子页显示，但这不再是“完全按 cue
     翻页”。当前代码在 (a)/(b)/(c) 之间没有决策，`unitPages()` 默认做了 (c) 的一部分，
     `CaptionOverlayV2` 又固定两行，二者不一致。

6. **引文/词边界**
   - 对 CJK 源，event 的 `from/to` 必须落在 ICU word boundary（至少不能落在词中）；
   - `source` quote 比较应允许标点归一（全角/半角、引号样式），或以 token 范围为主、
     quote 只做辅助校验；不能因为一个标点差异丢掉整个 block；
   - quote 失败时优先按单 cue 重试，而不是整块 4 cue 一起失败；块 7 的 13.875 s 空洞
     应被缩小到单 cue。

7. **计时能力验证与格式回退**
   - `RebuildSource.read()` 对所有格式设置 `formatEvidence = parsed.timingCapabilities()`；
   - `RawCaptionSource.load()` 解析后检查 `nativeWordCount()`/`coarseCueCount`；如果 ASR
     主源是 0 native，按 `SourceFormatPolicy.referenceProfiles()` 对**同一 track**尝试
     srv3/VTT/JSON3 变体；
   - `reference()` 不应只依赖 `NativeAsrTrackReference`；主源 `load()` 解析后
     `nativeWordCount()==0` 时，应直接以 source URL 的 `referenceProfiles()` 尝试同 track
     srv3/VTT/JSON3 变体，而不是等候选列表；候选列表仍可作补充；
   - 源缓存记录 `format/native_words/coarse_cues`，粗载荷命中时可升级而不是无条件复用；
   - 诊断增加 `detected_fmt/native_words/coarse_cues/timing_basis`，让下一次能直接判断。

8. **质量门禁去语言特判**
   - `RebuildSemantics.validate()`、`RebuildReview.inspect()` 的依赖/省略/数字检查不应只
     对 `en→zh` 生效；至少对 `ja→zh` 做：
     - 目标文字/残留源文检查；
     - ICU word boundary 检查；
     - 句末/名词短语/助词边界的 advisory/hard 规则；
   - 目标文字校验不能只查“有汉字”；应检查残留源语言词、混排比例、整句是否成句。

9. **诊断/测试**
   - `REBUILD_EVENTS_ACCEPTED` 增加 `cues`、`events_per_cue`、`cue_boundary_ok`；
   - `REBUILD_UNIT_MODE` 增加 `cue`、`cue_tokens`、`event_cue_map`；
   - 页面 `page_basis` 增加 `AUTHORED_CUE` / `SUBCUE_ESTIMATED`，不要把子 cue 页标成
     `SOURCE_EVENT`；
   - 新回归必须包含：
     - 400 cue 真实 VTT 上 `cue count == page count`、`page range == cue range`；
