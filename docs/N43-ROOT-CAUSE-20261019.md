## 0. 结论摘要

两个现象不是两组孤立 bug，而是同一类问题的两个出口：**关键决定没有单一权威**。

1. **语种记忆**：目标语言有 5 个写者（原生默认轨、原生选择事件、timed-text URL、一次性
   handoff、点击默认目标），生命周期各不相同；真正属于用户的记忆
   `RememberedCaptionSelection` 只在“原生默认轨选择器”里被查询一次，**对请求路径没有仲裁权**。
   引擎绑定的是当前 timed-text URL 的 `tlang`，所以“谁最后发请求，谁决定语言”。
2. **冷启动“已经是简体中文”**：代码里没有“用户尚未选择”这个状态。YouTube 自己持久化的
   自动翻译默认（本机为 `zh-Hans`）被应用**采纳**成当前选择
   （`applySelection(..., remember=true)`），此后所有读取“当前目标”的路径都把它当用户意愿。
3. **换视频仍回简体**：记忆按“轨道”寻址，新视频的翻译列表里没有该 code 时静默回退原生默认
   （本诊断的日语视频列表只有 3 项，记忆 `ko` 不在其中）；唯一能在请求路径上兜底的
   `CaptionVideoHandoffV2`，在真实视频切换顺序下被 `mayActivateAiTarget()` 判为 false 而
   **拒绝并清空**（探针可复现）；即使改写成功一次，同一视频的后续请求仍按 URL 的 `tlang`
   重新绑定。
4. **某些语种长时间无字幕**：`RebuildNumbers` 的数字 token 左边界只排除 ASCII 字母。
   西里尔/希腊字母后的连字符被读成负号：`Т-14` → `-14`，源 `t 14` → `14`，于是
   `numeric_substitution`，**整块**被丢弃；块级失败停留在 `WAITING`，进入**无上限慢重试**。
   诊断中同一块 56.5 s、8 次拒绝、9 次付费请求、21 帧等待记录，该块从头到尾没有译文。
5. **全语种翻页并不等价**：非 CJK 目标的页由几何（≤2 行）优先决定；阅读速率只惩罚
   “停留太久”，不惩罚“文字太密”。实测 es 7/7 页、vi 4/4、id 3/3、ru 11/14 超过该语言自己的
   cps 参考。页界落在分句上，但非 CJK 没有“引子不落页尾”规则。
6. **韩语被误分类为 compact（无词间空格）脚本**：合并事件丢空格
   （`10000대를\u200b시베리아` 显示为 `10000대를시베리아`），而 U+200B 又是合法页缝，
   于是可以在一个韩语词内部翻页。探针复现。

> 一句话：N40/N41/N42 各自修了“症状所在的层”，但“用户选择 → 目标语言 → 请求 → 引擎”这条链
> 始终没有被收成一个状态机；数字门禁始终在比较“像数字的字符串”而不是“数量表达式”。

## 1. 问题一：打开就是简体中文，换语种后其他视频仍是简体中文

### 1.1 契约是什么

- 补丁自己的描述（`patches-list.json:81-82`）：
  “Remembers caption language, source/translation mode and on/off selection across videos **for this
  app session**”。
- 项目文档写得更明确（`docs/VERIFICATION-1.0.3.md:18`）：
  “**每次进程冷启动首次选择语言**，此后跨视频记住开关、语言、原字幕/翻译模式和原字幕 ASR 偏好”。
- 用户本轮复述的期望：每次重开 YouTube 都要**手动**选一次自动翻译目标；之后本次进程内打开字幕
  自动选中该目标；视频自带目标译文时直接显示译文。

即三件事：**(a) 冷启动必须“未选择”**；**(b) 显式选择在进程内跨视频生效**；**(c) 目标选择必须
作用于每一次字幕请求，而不只是某一次默认轨**。当前实现三件都没有完整成立。

### 1.2 目标语言的五个权威

| # | 写者 | 生命周期 | 写什么 | 谁读 | 能否否决自动默认 |
|---|---|---|---|---|---|
| 1 | YouTube 原生默认轨（`origin=DEFAULT, reason=2`） | 播放器/账号持久 | 一条**轨道对象**（可带 `tlang`） | `followNativeSelection()` | 否 |
| 2 | 原生显式选择（`origin=PREFERRED_TRACK`） | 每次菜单选择 | `RememberedCaptionSelection` + `CaptionChoice` | 默认轨选择器、prewarm | 是（但只在 #1 的选择器里） |
| 3 | timed-text URL 的 `tlang` | 每个请求 | 引擎会话 target | `DeepSeekCaptionHook.rewriteUrl`、`RebuildController.activate` | **是（实际最终决定权）** |
| 4 | `CaptionVideoHandoffV2` | 视频切换后 12 s，一次性 | 改写一个请求的 `tlang` | 请求路径 | 有，但见 1.4 |
| 5 | `CaptionButtonController.rewriteDefaultTarget` | 点击 CC 后 2.5 s | 改写 `tlang` 为当前 choice | 请求路径 | 有，仅点击窗口 |

`CaptionChoice` 是第 6 个“半权威”：进程级、被当作“当前视频的选择”，但生产代码里**从不按视频
重置**——唯一调用 `CaptionChoice.reset()` 的 `NativeCaptionBridge.onVideoId()`
（`NativeCaptionBridge.java:645-661`）没有任何生产调用者（`grep` 全仓只有测试调用它）。
它的类注释说“this app launch”，但 `DeepSeekConfig.defaultTargetLanguage()` 又把它当“默认目标”
喂给 handoff 与点击路径（`DeepSeekConfig.java:252-254`）。

### 1.3 冷启动：没有“未选择”状态，自动默认被采纳

代码路径（全部在 `NativeCaptionBridge.java`）：

1. 冷启动时 `RememberedCaptionSelection.decision() == -1`，`resolveRemembered()` 返回 null
   （`:802-818`），patch 的默认轨钩子走 `:native_settings`
   （`NativeCaptionBridgePatch.kt:554-568`），即**原样使用 YouTube 的默认轨**。
2. 本机 YouTube 的默认轨是自动翻译 `zh-Hans`：诊断里凡记忆没有命中的模型初始化都是
   `origin=DEFAULT;translated=true;track=zh-Hans/manual`。
3. 该事件进入 `followNativeSelection()`（`:536-602`）：
   - `explicit=false`；
   - 1.6 的“忽略自动默认”守卫要求 `CaptionChoice.known()`，冷启动时为 false，**不生效**；
   - 于是 `applySelection(track, explicit || (!off && (!known || !userOff)))` = `applySelection(track, true)`
     （`:597-601`）；
   - `applySelection` 里 `if (remember) CaptionChoice.select(code, translate)`（`:619`）——
     **YouTube 的默认被写成了“用户选择”**。
4. 之后所有读取“当前目标”的地方（点击默认、prewarm、handoff 的无记忆回退）都得到 `zh-Hans`。

探针输出（`TmpLanguageAuthorityProbeTest`）：

```text
COLD memory.decision=-1 memory.language='' resolveRemembered=null restoreDecision=-1
COLD after automatic zh-Hans default: CaptionChoice.language=zh-Hans known=true on=true translates=true defaultTarget='zh-Hans'
```

结论：**“打开就已经选中简体中文”不是记忆被写坏了，而是应用把外部默认当成了用户选择**。
只要用户不先选一次，应用就没有办法区分“YouTube 记得简体”与“用户要简体”。要满足用户的
“每次重开都要手动选”，必须有一个真正的 `UNSET` 状态，并且它必须对请求路径有否决权。

### 1.4 跨视频：handoff 的结构性死锁（本轮新增证据）

`CaptionVideoHandoffV2` 是“换视频后把第一个请求改写成记忆目标”的唯一机制。它的执行顺序是：

```text
DeepSeekCaptionHookV2.onVideoId(video)                  (patched callback)
  ├─ CaptionVideoHandoffV2.onVideoId(video)             // 武装 pending
  └─ DeepSeekCaptionHook.onVideoId(video)
       ├─ CaptionActions.onVideoId -> CaptionApplication.command(VIDEO)
       │     └─ RebuildController.video(video)          // 见 RebuildController.java:452-475
       │           active=null, publicationEpoch++      // 旧会话被撤销
       └─ CaptionButtonController.onVideoId(video)      // 见 :138-157
             if (!CaptionActions.isVisibleActive()) captionIntent = UNKNOWN
```

`RebuildController.video()` 在视频变化时撤销旧会话，因此紧接着的
`CaptionActions.isVisibleActive()` 为 false（`visible()` 要求 `active` 是该视频的当前会话，
`RebuildController.java:433-436`），`captionIntent` 被置为 `UNKNOWN`。
下一次 timed-text 请求到来时：

```text
CaptionVideoHandoffV2.restoreForNextVideo()            // :52-86
  if (!CaptionButtonController.mayActivateAiTarget()) { clearPending(); return url; }
```

而 `mayActivateAiTarget()` = `now > nativeMenuUntilMs && CaptionIntentPolicy.mayActivate(captionIntent, …)`
（`CaptionButtonController.java:214-218`），`mayActivate` 只有 `intent == ON` 或点击窗口内才为真
（`CaptionIntentPolicy.java:45-47`）。视频切换刚把 `selectDefaultUntilMs` 清 0，所以**必然为 false**。
pending 被清空，请求保持 YouTube 的 `tlang=zh-Hans`。

更根本的是这个顺序是**循环依赖**：`captionIntent=ON` 的证据来自 CC 按钮（或已可见的 AI 会话），
而 CC 按钮变 ON 恰恰发生在 YouTube 已经应用了默认轨**之后**——也就是发生在需要被改写的那个请求
**之后**。handoff 要求“新视频已经证明用户想要字幕”，但它要改写的正是让字幕出现的那次请求。

探针（真实调用顺序）复现：

```text
HANDOFF mayActivateAiTarget=false captionIntentKnownOn=false memory=ko
HANDOFF result=REFUSED (request keeps tlang=zh-Hans)
HANDOFF with intent ON mayActivateAiTarget=true result=rewritten to tlang=ko
```

第三行说明：只要先把 `captionIntent` 强成 ON，handoff 是好的——这正是现有回归测试
`N40LanguageMemoryTest.handoffUsesRememberedTargetAfterCurrentChoiceWasCorrupted`
（`extensions/.../N40LanguageMemoryTest.java:70-83`）在 `:74` 调 `noteAiTrackSelected()` 的原因。
**该测试测的是生产在那一刻不可能出现的状态**，所以它一直是绿的，而真机路径一直不生效。

诊断侧的旁证：整份文件 19 次菜单构建、25 次轨道应用、11 次会话绑定，`VIDEO_DEFAULT_AI_RESTORED`
出现 **0 次**（N40 报告里同款诊断也是 0 次）。不是“偶尔没赶上”，是这条路径从未成功。

### 1.5 记忆只能按“轨道”寻址

`resolveRemembered()`（`NativeCaptionBridge.java:802-818`）做的事是：

```java
List<?> list = translated ? translatedTracks(manager) : nativeTracks(manager);
for (Object track : list)
    if (RememberedCaptionSelection.language().equals(language(track))) { ... return track; }
return fallback; // 可能为 null
```

它必须在新视频的**当次原生轨道列表**里找到同 code 的轨道。找不到就返回 null，patch 的默认轨钩子
回退到 `native_settings`（`NativeCaptionBridgePatch.kt:559-568`）——也就是 YouTube 的默认轨。
这是“记忆存在但静默失效”的入口，`ModularCaptionTest.missingLanguageDoesNotFabricateATrack`
（`extensions/.../ModularCaptionTest.java:59`）把它写成了预期行为。

本诊断的直接实例：

| 时刻（uptime ms） | 事件 |
|---|---|
| `1792418105953` | 用户显式选 `ru`：`origin=PREFERRED_TRACK;reason=1;track=ru/manual` |
| `1792418177385` | 显式选 `vi` |
| `1792418188895` | 显式选 `id` |
| `1792418199458` | 显式选 `es` |
| `1792418212411` | 显式选 `ko` |
| `1792418235850` | 下一个视频自动默认 = `ko`（记忆命中，工作正常） |
| `1792418241876` | 切到日语视频：`LANGUAGE_MENU_READY selected=2;items=3`（该视频翻译列表只有 3 项） |
| `1792418241900` | 默认轨 `origin=DEFAULT;track=zh-Hans/manual`（记忆 `ko` 不在列表 → 回退原生默认） |
| `1792418241980` | `LANGUAGE_PROFILE_BOUND session=113;source=ja;target=zh-Hans`（引擎已绑简体） |
| `1792418242053` | `NATIVE_SELECTION_IGNORED reason=user_choice_kept;current=ko;native=zh-Hans` |

注意最后两行的顺序：**引擎先按 zh-Hans 绑定了会话，之后“保留用户选择”的守卫才看到事件**。
守卫只能阻止 `followNativeSelection` 去停/换会话，不能把已经绑定的 target 改回 `ko`。

还有一次同类回退，说明记忆命中还依赖“默认选择器执行时模型/列表是否已就绪”：

| 时刻 | 事件 |
|---|---|
| `1792418251597` | 切到一个英语视频：`LANGUAGE_MENU_READY selected=2;items=17` |
| `1792418251610` | `origin=DEFAULT;foreground=false;track=zh-Hans`（此时记忆仍是 `ko`；此后到导出前没有新的显式选择） |
| `1792418251637` | `LANGUAGE_PROFILE_BOUND session=1;source=en;target=zh-Hans` |

也就是说，即使记忆仍是 `ko`，默认选择器这一次也没有命中它。可能是该视频的列表没有 `ko`，
也可能是默认选择器执行时列表还没就绪（同一进程里 `1792418235850` 的另一次 en 视频默认曾命中
`ko`）。诊断没有记录 `memory decision/language` 与 `resolveRemembered` 的返回值，无法区分
“没有武装”“列表未就绪”“列表里没有”，这本身就是需要补的可观测性（见第 5 节）。

### 1.6 请求路径没有仲裁权

`DeepSeekCaptionHook.rewriteUrl()`（`DeepSeekCaptionHook.java:74-152`）的决策顺序：

1. 计算 `translated = TargetLanguage.fromUrl(originalUrl) != null`；
2. 翻译请求的“证据”检查 `selectionEvidence()`（`:159-165`）：
   `isVisibleActive() || CaptionChoice.isOn() || mayActivateAiTarget() || nativeMenuRecentlyOpened() || captionsKnownOn()`；
3. `selectionEvidence` 为真就继续；`intercepted = TargetLanguage.fromUrl(selected) != null && (isVisibleActive || mayActivate || translated)`——
   **对已经是翻译的请求，`|| translated` 恒真**；
4. `CaptionActions.activate(context, selected)` 用 `selected`（其 `tlang` 就是 URL 带来的那个）启动引擎。

也就是说：请求路径**从不把 `RememberedCaptionSelection` 当作目标**，只用它判断“要不要拦截”。
`CaptionLifecycleRestore.restoreAfterLifecycle()`（`CaptionLifecycleRestore.java:32-43`）确实会把
“同一个可见会话的**非翻译**源请求”改成当前 target，但它明确跳过 `TargetLanguage.fromUrl(url) != null`
的请求——翻译请求永远保留自己的 `tlang`。

补充：`CaptionButtonController.rewriteDefaultTarget()`（`:235-258`）只在短按 CC 后 2.5 s 的窗口内
改写，且读的是 `DeepSeekConfig.defaultTargetLanguage()`（当前 choice），与记忆无关。

### 1.7 为什么 N40 的修复没有闭环

N40 根因报告（`docs/N40-ROOT-CAUSE-20261019.md:166-188`）已经指出 R1-2/R1-3：

- 记忆没有请求路径上的仲裁权；
- handoff 恢复的是 `defaultTargetLanguage()`（当前 choice），不是记忆。

N40-REPAIR 实际做的是：handoff 改读记忆（`CaptionVideoHandoffV2.java:68-85`）、
自动默认不再覆盖 choice、克隆轨保留 code、空 code 不再默认简体。
但：

- handoff 仍然是一次性、仍被 intent 门禁卡住（1.4）；
- 请求路径仍然按 URL 绑定（1.6）；
- “自动默认不能覆盖用户选择”只做成了**忽略**，不是**改回**；
- 冷启动的“自动默认被采纳”没有被触碰（1.3）。

所以 N40 的修复让“有记忆且新视频列表里有该语言”这一种情况可用（诊断里 `ko` 的那次），
但另外两条主路径（冷启动、列表里没有该语言）仍然回到简体。

### 1.8 本问题的根因陈述

- **R1（状态模型）**：没有“用户尚未选择”的一等状态；`CaptionChoice` 把“播放器应用了一条轨”
  与“用户选择了这条轨”混为一谈，于是 YouTube 的持久默认在冷启动被采纳。
- **R2（寻址方式）**：记忆被建模成“在当次原生轨道列表里找同 code 的对象”，因此它的生效
  依赖每个视频的翻译列表；列表里没有就静默回退原生默认。记忆本该是**与列表无关的 target code**。
- **R3（权威位置）**：唯一真正的 target 写者是 timed-text URL。记忆、handoff、点击默认都只是
  “改写某一个请求”的机会，而不是“每个前台请求都必须满足的不变量”；且唯一常驻的兜底
  （handoff）被一个只能在请求之后才成立的门禁锁死。

### 2.2 数字门禁的 ASCII 左边界

`RebuildNumbers.NUMBER`（`RebuildNumbers.java:39-40`）：

```java
Pattern.compile("(?<![a-zA-Z0-9])[+-]?\\d+(?:,\\d{3})*(?:\\.\\d+)?");
```

左边界 `(?<![a-zA-Z0-9])` **只排除 ASCII 字母和数字**。对 `Т-14`（西里尔 Т）：

- 匹配从 `-` 开始（`-` 前一个是 `Т`，不在 `[a-zA-Z0-9]` 里，lookbehind 通过）；
- 于是 token 是 `-14`，`BigDecimal` = **-14**。

而源文 `t 14`（ASR 把 `T-14` 拆成 `t` 和 `14`）匹配到的是 `14`。
`compare()` 在“两边各一个值”时直接判不等（`RebuildNumbers.java:215-227`）：

```java
if (left.size() == 1 && right.size() == 1)
    return left.get(0).compareTo(right.get(0)) == 0 ? EQUIVALENT : CONTRADICTED;
```

探针输出（`TmpNumberDesignationProbeTest`）：

```text
VALUES source(t 14) = [14]
VALUES ru(Т-14)   = [-14]
COMPARE en->ru = CONTRADICTED ; source_values=[14];target_values=[-14]
BOUNDARY ASCII    'T-14'   -> [14]
BOUNDARY CYRILLIC 'Т-14'   -> [-14]
BOUNDARY GREEK    'Τ-14'   -> [-14]
BOUNDARY MiG      'МиГ-29' -> [-29]
```

这不是“俄语模型翻错了”：`Т-14` 是正确的俄语写法，`-14` 是**校验器自己**产生的 token。
同理，任何“非 ASCII 字母 + 连字符 + 数字”的型号都会中招：`МиГ-29`、`Су-57`、
希腊字母型号、以及“源是西里尔、目标是拉丁”的反向组合。

### 2.3 为什么这是“深根”，不是再调一个阈值

同一个门禁还有两种相反的错误形态，说明问题不在阈值，而在**它把“像数字的字符串”当成“数量”**：

1. **同一个会话里的假阳性**：`session 17`（en→zh）在 `1792418262825` 因
   `source_values=[2E+2];target_values=[2E+8]` 拒绝整块——源文是 `200 megapix`，译文是
   `2亿像素`，两者是**同一数量的不同单位**。模型后来把同块重写成包含 `1300` 与 `2亿` 的两值事件，
   `compare()` 因“多于一个值”退化为 `UNKNOWN` 而接受（`1792418265501`）。
   同一对数字，取决于**模型怎么切事件**，一次被拒一次被放行。
2. **标识符 vs 数量**：`T-14` 是名称，`14` 是名称里的编号，不是可比较的量。门禁没有“这是型号/
   名号”的概念；`RebuildSemantics` 里明明有 `MODEL`/`TANK_MODEL` 正则
   （`RebuildSemantics.java:20-45`），数字层却没有使用它。

N42 已经修过“数值的表示形式”（`4 and a half` → `4.5`），但那是**扩展数字语法**；
本轮暴露的是**词法边界**与**语义类别**的问题——继续往 `NUMBER` 里加分数/单位，只会同时
扩大假阴性和假阳性，不会解决“型号里的数字被当成数量”。

### 2.4 整块 fail-closed + 无上限慢重试

`RebuildProtocol.java:397-401`：一个 event 数字冲突就 `throw new Invalid("numeric_substitution")`，
整个 block（自动源 8–11 个 event、约 23 s 内容）**一个都不发布**。

`RebuildController.rejected()`（`:1626-1696`）：`numeric_substitution` 不是 fatal、不是
content_filter，所以 `s.states[i] = WAITING`；`structuralRetry()` 又不含它
（`RebuildReview.java:551-565`），`maxAttempts = 2`。当尝试用尽且没有 plan 时
（`:1407-1430`）：

```java
// A block that never produced anything keeps a slow, bounded-rate retry
// while it is still in front of the viewer, instead of disappearing for good.
if (now < s.retryAt[i]) continue;
s.attempts[i] = Math.max(0, maxAttempts - 1);
slowRetry = true;
```

于是**只要观众还停在这个块，就永远重试**：每次都是同一个确定性判断，每次都是付费请求。
诊断里的 56.5 s / 8 次拒绝 / 9 次请求就是这么来的（相邻拒绝间隔 3.2–8.9 s，最长 17 s；
退避在 `:1666-1671` 封顶 15 s）。

同一份诊断里 `numeric_substitution` 的失败分布（按会话）：

```text
session 17  rejected: numeric_substitution ×1（200 megapix → 2亿）
session 58  rejected: numeric_substitution ×6, source_quote_mismatch ×1, json ×1   (全部 block=4)
```

### 2.6 根因陈述

- **R4（词法）**：数字 token 的左右边界只按 ASCII 定义，非 ASCII 字母与连字符相邻时，
  连字符被当作符号位。结果是“俄语/希腊语等目标把型号写成 `Т-14`”这一类**正确译文**被读成
  `-14` 并与源的 `14` 冲突。
- **R5（语义）**：门禁没有“数量”与“标识符/名号”的分野，也没有单位/量级语境；它用
  “1:1 值相等”做硬拒，用“多值/缺值”做放行，导致同一错误一次拒一次过。
- **R6（失败粒度与重试）**：拒绝粒度是整块，失败状态是可无限重试的 `WAITING`；
  确定性拒绝没有“同一原因不再付费重试”的记忆，于是把一次词法误判放大成整段无字幕 + 持续扣费。

## 3. 问题二 B：全语种适用性与翻页是否合格

### 3.1 页面身份与时间基线

- 页面是**模型 event** 的投影：`RebuildDisplayGroups.partition()` 把相邻 event 合成 display
  unit，`RebuildPageLayout.unitPages()` 再在 unit 内切页；`CaptionLanguagePager.plan()` 是入口
  （`CaptionLanguagePager.java:23-39`）。
- 时间基线：自动源本诊断全部 `precision=native=0; estimated=<全部词>; coarse_reconstructed=true;
  detected_fmt=json3`，且 `ASR_REFERENCE_UNAVAILABLE reason=no_usable_timing`
  （`1792418106376`、`1792418177826`…）。也就是说自动源的页窗是**cue 级重建**的估计；
  人工源（日语视频）是 `AUTHORED_CUE` 精确 cue 窗。
- 页时间基准分布（`REBUILD_PRESENTED.page_basis`）：`SOURCE_EVENT` 49、`AUTHORED_CUE` 28、
  `ESTIMATED_PAGE_TIMING` 10（多页切分全部落在这 10 条）。

### 3.2 实测阅读速率

用诊断自己的 `reading_units / duration_ms`（按其 `reading_rate_limit` 判定）：

| 目标 | 页记录 | 超限页 | cps 最小/最大/均值 | 该语言参考 |
|---|---:|---:|---|---:|
| zh-Hans | 50 | 2 (4%) | 4.3 / 12.8 / 6.0 | 9 |
| ru | 14 | 11 (79%) | 14.4 / 23.6 / 18.3 | 17 |
| es | 7 | 7 (100%) | 18.8 / 32.5 / 25.8 | 17 |
| vi | 4 | 4 (100%) | 18.7 / 23.4 / 20.2 | 17 |
| id | 3 | 3 (100%) | 19.5 / 25.6 / 22.4 | 17 |
| ko | 9 | 1 (11%) | 6.3 / 13.8 / 9.4 | 12 |

（`reading_units` 把空格也算进去了，见 3.6。按 Netflix 的计数规则，Latin 文字的空格/标点本来
就计入阅读速度，所以这里的 cps 与 Netflix 口径一致；只有韩语/中日等“半角字符计 0.5”的规则
app 一律计 1，方向偏保守。上述超限仍然成立。）

差异不是“模型对某些语言更啰嗦”这么简单：**中文的事件天然短、页落在 4–7 cps；字母语言的
事件天然长（40–90 字符），而页规划只要“两行放得下”就整段成一页**。

### 3.3 机制：几何优先，时间只惩罚“太久”

`RebuildPageLayout.unitPages()`（`:108-167`）的顺序是：

```java
if (spec.authored && twoLines) return singleton(Page(text, start, end, "AUTHORED_CUE"));
if (twoLines && (cuts.isEmpty() || !timeSplitWanted(text, start, end, spec)))
    return singleton(Page(text, start, end, "SOURCE_EVENT"));   // ← 非 CJK 的绝大多数页
```

`timeSplitWanted()`（`:175-193`）只在 **`duration > comfortMs`** 时返回 true；
`comfortMs = clamp(reading × 1.5, 3000, 5000)`。也就是说：

- **页停留太久**（文字少、窗口长）会被切成多页；
- **页文字太密**（窗口短、文字多）**没有任何规则**：不会切，也不会降级/缩短。

即使走到多页搜索 `CaptionLanguagePager.choose()`（`:388-487`），打分顺序是
emergency → weak → longPages → clauses → pages → balance，**没有“每页阅读时间下限”**；
`MIN_PAGE_MS = 1200` 只限制“最多能切几页”，不保证“每页够读”。
合并层 `RebuildDisplayGroups.readable()`（`:318-337`）甚至显式允许 4/3 倍参考速率：

```java
units * 3000L <= duration * spec.profile.referenceCps * 4
```

这解释了 ru 的 23.6 cps（17 × 1.39）和 es 的 32.5 cps（17 × 1.9）。

### 3.4 非 CJK 没有“引子不落页尾”规则

中文路径有 P3 规则（引子分句不落页尾，`RebuildPageLayout.pack/foldTinyOrLeadPages`，
`leadLimit = max(4, referenceCpl/2)`），但它只在“文本超过两行”的分支里生效；
超过两行的多页搜索走的是 `CaptionLanguagePager.choose()`，那里只用 `clauses` 计数惩罚分句断点，
没有“这个分句是不是引子”的概念。

诊断实例（`58:0:2:145-163`，device 实测）：

```text
page 1/2  'Потому что, хотя, как мне кажется,'          (1974 ms, 35 units, 17.7 cps)
page 2/2  'Россия очень хорошо преувеличивает свою международную репутацию и военные возможности,'
```

第一页是纯引子（“因为，虽然，在我看来，”）。中文的同类文本会被并到下一分句；俄语不会。
这不是“翻页位置漂移”，而是**页边界语义规则只对中文实现过**，N42 去中文特例时没有把这条规则
提升为语言无关规则。

### 3.5 韩语：Hangul 被当作 compact 脚本

`CaptionScript.compact()`（`:29-43`）把 HANGUL 列进“不写词间空格”的脚本：

```java
case UScript.HAN: case UScript.HIRAGANA: case UScript.KATAKANA: case UScript.HANGUL:
case UScript.THAI: case UScript.LAO: case UScript.KHMER: case UScript.MYANMAR: return true;
```

这是事实错误：韩语用空格分隔 **eojeol（어절）**。后果有两个：

1. **合并事件丢空格**。`RebuildDisplayGroups.separator()`（`:369-383`）对 compact 脚本
   在无标点边界返回 `""` 或 `U+200B`，永远不是空格：
   ```text
   JOIN ko no-break  : '[ZWSP]'
   JOIN ko continuous: ''
   JOIN ru no-break  : ' '
   ```
   真实诊断行（`id=97:0:1:88-97`）：
   ```text
   text=이반이 T-62 10000대를\u200b시베리아 어딘가에서 녹슬게 방치하고 있다면.
   ```
   屏幕上是 `10000대를시베리아`——少一个空格。
2. **U+200B 是合法页缝**。`CaptionLanguagePager.protectedOffsets()`（`:171-208`）只保护数字和
   `-./_` 复合标识符；`legal()`（`:232-241`）不把 U+200B 当空白，所以切在 U+200B 上是合法的。
   对被误判为 compact 的韩语，这意味着**可以在一个词内部翻页**（例如 `폭` + `\u200B` + `격기`）。

同一份诊断里 `97:0:1:73-87` 的 `스텔스 폭 격기`（半角空格）是模型自身的韩语分写错误，
与本机制无关；但 `10000대를\u200b시베리아` 的缺空格是本机制的直接结果。

### 3.6 阅读单位把空格算进去（与 Netflix 口径一致，但不是全脚本一致）

`CaptionUnicode.readingUnits()`（`:172-184`）数的是“可见 grapheme”，而
`invisible()`（`:141-148`）只排除组合符号/格式/控制/行分隔符，**不排除空格（Zs）**。
探针：

```text
UNITS ko with spaces    = 21
UNITS ko without spaces = 18
UNITS en 'T-14 tank'    = 9
```

韩语同一句话，带空格多出 3 个单位；英语 `T-14 tank` 的 9 个单位里有 1 个是空格。
需要更正一个容易产生的误判：Netflix 的 QC 规则**明确把空格和标点计入**阅读速度
（<https://partnerhelp.netflixstudios.com/hc/en-us/articles/115001352212-How-is-reading-speed-measured-Do-punctuation-and-spaces-count>），
所以对 Latin 文字而言，app 的计数与 Netflix 口径一致，不是缺陷。真正的差异只有：
Netflix 对韩语/中日等“半角字符”按 0.5 计，app 一律计 1（偏保守）；以及 app 把同一套
`referenceCps` 用于“停留太久”的判断，却从不用于“文字太密”的下限（3.3）。

### 3.7 语种覆盖与方向

- `CaptionLanguageProfile`（`:51-62`）只有 14 个具名 profile + `GENERIC`
  （17 cps / 42 cpl / GRAPHEME / FIRST_STRONG）。除这 14 个之外的任何目标
  （uk、tr、pl、cs、th、he、fa、ur…）都落到 GENERIC。
- `CaptionLanguageSelection.CODES`（`:20-24`）也只有这 14 个；设置页只能“把语言加入菜单”，
  用户仍可在 YouTube 原生菜单里选其它语言（本诊断的 ru/vi/id/es/ko 都是原生菜单选的）。
  一旦选了列表外语言，没有对应的 cps/cpl/方向 profile 可依。
- 只有 `ar` 被登记为 RTL；`he`/`fa`/`ur` 落到 GENERIC 的 `FIRST_STRONG`。
  `CaptionRenderSpec.apply()` 对 GENERIC 设 `LAYOUT_DIRECTION_LTR`（`:150-162`），
  `heuristic()` 返回 `FIRSTSTRONG_LTR`（`:142-148`）。对整行 RTL 文本，ICU 的
  FIRSTSTRONG 仍会判 RTL，但方向契约没有被显式建模，也没有测试覆盖。

### 3.8 哪些是合格的（正例）

- **页界落在分句上**：本诊断所有多页页界都落在逗号/冒号/句末之后，没有在词中切（韩语 ZWSP
  是例外，见 3.5）；`ClausePaginationTest` 也覆盖了这一点。
- **人工 cue**：28 个 `AUTHORED_CUE` 页使用作者 cue 的精确窗口（日语视频），没有估算漂移。
- **单页事件**：49 个 `SOURCE_EVENT` 页整段使用事件窗口，边界精确。
- **目标语言已自带译文时直接显示**：`SourceTrackPolicy.ownTargetTrack()` 存在并接在
  `rewriteUrl()` 上（`DeepSeekCaptionHook.java:131-136`），但本诊断 0 次
  `SOURCE_TRACK_OWN_TARGET`——这些视频都没有目标语言的原生轨，因此这条**无法在本次证据中确认**。

### 3.9 根因陈述

- **R7（时间预算）**：页契约是“几何优先”：能放两行就是一页；阅读时间只在“停留太久”时参与，
  不约束“文字太密”。对事件更长、语速更快的字母语言，页密度系统性超过参考。
- **R8（语义规则）**：引子/残尾规则只在中文的“超过两行”分支实现，多页搜索与非 CJK 没有。
- **R9（文字属性）**：`compact` 把 Hangul 当无空格文字，既丢词间空格，又把 U+200B 变成
  词内页缝；`reading_units` 又把空格计入，跨脚本不可比。
- **R10（覆盖）**：14 个 profile 之外的语种只有 GENERIC，RTL 只登记 ar；没有“所有可被
  YouTube 选中的目标语言”的覆盖保证。

## 4. 两个问题的共同结构

| 层 | 现在的事实 | 后果 |
|---|---|---|
| 用户选择 | 没有 `UNSET`；自动默认被采纳为 choice | 冷启动即简体；无法“每次手动选” |
| 目标语言 | 记忆按轨道寻址；请求按 URL 的 tlang 绑定；handoff 一次性且被循环门禁锁死 | 换视频/换语种回到原生默认 |
| 数字身份 | 词法边界 ASCII-only；数量与标识符不分；整块 fail-closed + 无界重试 | 某些语种整段无字幕 + 持续扣费 |
| 页契约 | 几何优先；时间只惩罚太久；引子规则只在中文分支；Hangul 当 compact | 非 CJK 页过密、引子落页尾、韩语丢空格/词内翻页 |

共同点：**每一层都有多个“看起来像权威”的东西，但没有一个状态机规定谁优先、谁能否决、
谁必须在每个请求上被重新满足。** N40/N41/N42 的修复分别落在不同层，都是“让某个症状在
某个样本上消失”，没有改变这个结构，所以新的诊断又长出同族的症状。

## 5. 建议的结构性方向（本轮不改代码）

1. **一个选择状态机**（替代 1.2 的五个权威）：
   `UNSET | OFF | SOURCE_ONLY | TRANSLATE(code)`。只有显式用户事件（原生菜单
   `PREFERRED_TRACK`、应用自己的菜单、点击默认目标）能离开 `UNSET`；自动默认/DEFAULT 事件
   只能作为建议，不能写入状态。冷启动的 `UNSET` 必须对翻译请求有否决权（保持源字幕或原生
   默认，不启动付费翻译），直到用户选一次。
2. **一个 target 不变量**（替代 handoff/点击/生命周期三条改写路径）：
   只要状态是 `TRANSLATE(code)`，前台视频的**每一个** timed-text 请求在进入引擎前都必须
   被改写成该 code；允许多次、幂等、与 intent 无关；只有该视频的显式新选择能改变它。
   视频自带该语言轨道时走 `ownTargetTrack()`（已有），不发 API。
3. **一个数字身份模型**：把“数量”与“标识符/名号”分开。
   - 词法边界用 Unicode 字母（`\p{L}`）而不是 `[a-zA-Z]`，并对“连字符+数字”只在
     `-` 前是空白/开括号/运算符时才视为符号位；
   - 识别 `MODEL`/`TANK_MODEL` 这类“字母+连字符+数字”的复合标识符，整体比较而不是拆成数字；
   - 比较单位/量级语境（`200 megapix` ↔ `2亿像素`），不确定时保持 `UNKNOWN` 而非硬拒；
   - 若仍拒绝：记录“确定性拒绝原因”，同一块同一原因不再付费慢重试（或按指数退避封顶）。
4. **一个页契约**：输入（源语句边界 + 译文 + 时间窗 + 几何）→ 输出页；规则语言无关：
   - 页界只落在完整分句；引子/残尾规则对所有语言生效（从 `unitPages` 提到 `choose()`）；
   - 页密度有下限：一页的阅读时间不得超过窗口（否则优先在分句处切页；切不动则标记
     `dense_page` 诊断，作为译文过长/模型分段的证据）；
   - `MIN_PAGE_MS` 同时是“页阅读时间下限”的依据，而不是只限制页数。
5. **文字属性修正**：Hangul 从 `compact` 移除（韩语是有空格文字）；U+200B 只作为
   Han/Kana/Thai 等的词内页缝，且在韩语/拉丁语境下不得作为页界；`reading_units` 排除空格
   或明确把 cps 定义为“含空格字符/秒”，二者取一并写进诊断版本号。
6. **可观测性**：本轮两次都因为诊断缺少关键状态而无法区分路径。至少增加：
   `LANGUAGE_STATE`（state/decision/code/来源）、`TARGET_REQUEST`（URL 的 tlang、是否被改写、
   改写者、intent 证据）、`PAGE_DENSITY`（每页 units/cps/limit/是否超限）。

## 7. 边界与未决

- 本轮的“冷启动”结论由代码路径 + 探针证明；诊断文件本身是在进程运行中导出的，不能直接
  证明“本次是冷启动”。但诊断里多次 `origin=DEFAULT;track=zh-Hans` 证明 YouTube 的默认轨是
  自动翻译，且应用没有区分它与用户选择。
- `VIDEO_DEFAULT_AI_RESTORED=0` 证明 handoff 从未成功；由于诊断没有记录 pending 是否武装、
  `captionIntent` 的值，无法从日志区分“未武装”与“被 intent 门禁清掉”。探针按真实调用顺序
  复现了后者；前者只影响“是否武装”，不改变“请求路径没有仲裁权”的结论。
- 日语视频翻译列表只有 3 项、英语视频 17 项，是诊断计数；其上游原因（YouTube 对该视频的
  `translationLanguages` 内容）不在本仓库控制范围。但它足以证明“记忆按轨道查找”会在某些
  视频上失败。
- `numeric_substitution` 的 `-14` 来自生产 `RebuildNumbers` 的探针重放；本诊断没有保留 block 4
  的原始回复正文（质量证据只留最后 6 条），但 `source_values=[14];target_values=[-14]` 是
  生产代码自己写下的判定，已足以定位。
- 韩语的 `10000대를\u200b시베리아` 是诊断文本的直接证据；页面是否真的在该 ZWSP 处翻页，
  本诊断没有出现（该页是 1/1），但 `legal()`/`protectedOffsets()` 的代码路径允许它。
- 非 CJK 页的 cps 统计包含空格；不同字体度量下 Robolectric 复现不了设备的精确页宽，
  因此 3.4 的页边界以设备诊断文本为准，探针只证明“页密度不设下限”的机制。
- 本轮没有连接、安装或写入手机；没有修改产品代码；没有重新构建 MPP。
