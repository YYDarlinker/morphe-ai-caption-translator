## 0. 一句话结论

四个现象不是四个独立 bug，而是三条结构性断链的出口：

1. **显示页的权威没有统一**：人工 cue、模型 event、显示 group、分页页、overflow 子页是
   四套身份。人工 cue 只在“能放进两行”时是页；一旦超过两行，代码悄悄退回“按标点切”的
   另一条路径，既不声明 overflow，也不保证不空屏；而“不能独立成页”的碎片 cue（`が`、
   `しかし`）又被当成不可违反的页边界，导致整块译文被拒。
2. **语言被当成布尔值**：`CaptionRenderSpec` 用“目标是不是中文”选择两套完全不同的分页器，
   并且 `compactScript = chinese` 让日语/韩语/泰语按“有空格文字”处理；质量门禁又用
   `canApplyEnglishToChinese` 把 `ja→zh` 等语言对整体跳过。所谓“日语优化”是数据里的一个
   特例，不是语言中立的机制。
3. **数字身份按字面比较**：`4 and a half` → `4.5` 被判成 `numeric_substitution`，整块
   4–8 条译文全部丢弃；加上 block 级 all-or-nothing，用户看到的就是“翻译中…”。

显示时长的直接原因则是第 1 条的另一面：**只要译文能放进两行，分页器就返回单页并占用整个
unit 窗口**，按阅读量/时长切页的搜索根本没有被调用。诊断里 5–7.4 s 的页面不是“阅读速度
不够”，而是“几何优先”的页规划把时间排除在页边界标准之外。

## 1. 问题一：人工 cue 不可切且超过两行时的兜底

### 1.1 设计意图与实现的差距

设计要求（本轮用户明确）：人工 cue 是不可切的显示边界；当 cue 的译文超过两行时，采用自动
翻译字幕的那一套“语义 + 标点 + 句子长短 + 对应时间长短”的分页逻辑，而不是截断、空屏或
悄悄按字符比例切。

现行链路（修复前）：

```text
planAuthored() → Block.cues（原始 cue）
  → RebuildApi.prompt()/payload（N41 已带 cue 契约）
  → RebuildProtocol.parseBound()
  → RebuildCueContract.validate()/units()（一个 cue 一个 Unit）
  → RebuildPageLayout.unitPages()
       if (fitsOne || authored && fitsTwo) return singleton(AUTHORED_CUE)
       else 按标点 pack() 成一行一页，basis=SOURCE_EVENT
  → TranslationPresentation.pages()
       planner 为空 → fullPage()（完整文本，可能 >2 行）
  → CaptionOverlayV2（TextView maxLines = 2）
```

三个结构性缺口：

1. `unitPages()` 的 early return 只问“能不能放进两行”。超过两行时才进入 `pack()`，
   而 `pack()` 只按标点做一行一页；它没有“overflow 是人工 cue 的显式子页”这个身份，页
   的 `timingBasis` 仍是 `SOURCE_EVENT`，诊断无法区分“作者页”与“溢出子页”。
2. 当 cue 内没有标点、或单个分句超过两行时，`pack()` 返回 null，`plan()` 进入
   `CaptionLanguagePager` 的 fallback；fallback 在修复前只按 `cuts` 找前缀，找不到时
   可能把整段作为一个 >2 行页返回。`TranslationPresentation.fullPage()` 也会返回完整
   文本。覆盖层随后只能 `overflow_status` / `unprojectable_pixel_width` 空屏，或者被
   TextView 截断。
3. 更隐蔽的一条：**“不能独立成页”的碎片 cue 被当作不可违反的 cue**。诊断 session 1
   的真实 VTT cue 47 是 `が`（458 ms，1 个可见字符），cue 48 是 `しかし`（667 ms）。
   模型把 token 868–871 合成一个事件（`がしかし`），这是语言学上正确的合并；但
   `RebuildCueContract.validate()` 只查 `words[from].cue == words[to].cue`，于是
   `authored_cue_boundary`，整块 4 个 cue（150.250–157.167 s）全部不发布。重试 4 次
   （请求 24/25/33/35）都得到同一结果，用户看到 6.9 s 的“翻译中…”。
   这不是“cue 超过两行”，但属于同一类“cue 作为显示边界不可执行”的问题：作者写了一个
   不能单独阅读的页，契约却要求模型和显示层都把它当成完整页。

### 1.2 真实数据复现

`b12_868_892`（session 1，`FzRyrjFmZSQ`，人工轨）：

```text
BLOCK b12_868_892 cues=4
CUE 47 868-868 source=が
CUE 48 869-871 source=しかし
CUE 49 872-890 source=もう一点注目すべきはサイト内のこの表記
CUE 50 891-892 source=「AppleUnsoldはAppleと提携していない」
```

修复前的诊断拒绝：

```text
block=12;reason=authored_cue_boundary; range=868-871; merges cue 47 into cue 48
```

修复后同一 block 的显示 group：

```text
GROUP 47 868-890 source=がしかしもう一点注目すべきはサイト内のこの表記
GROUP 50 891-892 source=「AppleUnsoldはAppleと提携していない」
PARSED events=3
UNITS=2
UNIT 150250-154292
UNIT 154292-157167
```

即：`が`+`しかし`+下一句合成一个 4.04 s 的页，`50` 仍按作者 cue 成页；模型 868–871 的
事件落在这个 group 内，不再被拒。证据文件
`validation/runs/20261019-n42-root-cause/real-vtt-probe-output.txt`。

### 1.3 根修方向（已实施）

1. **Display group**：`RebuildCueContract.groups()` 在请求、校验、显示、缓存四处使用同一组
   边界。普通 cue 仍是一组；只有“不能独立成页”的 cue 才向前合并：
   - 可见字符 ≤ 2；
   - 整段由虚词/连接词组成（`が`, `しかし`, `そして`, `また`, `一方`, `另一方面`, …）；
   - 时长 < `MIN_GROUP_MS/2`（600 ms）。
   合并后的 group 继续吸收后续 cue，直到能成为可读页；block 末尾的碎片向后并入。
   `RebuildCueContract.VERSION` 升到 `authored-cue-v2`，缓存 identity 同步失效旧页。
2. **显式 overflow**：人工 cue/group 的译文 > 2 行时：
   - `unitPages()` 仍用整套 clause packing / measured fallback；
   - 如果单个分句本身 >2 行，`splitToFit()` 在字形边界上切成 ≤2 行子页；
   - 所有子页标记 `AUTHORED_OVERFLOW`，页窗仍严格落在 cue/group 的外窗内；
   - 不再把 overflow 页伪装成 `SOURCE_EVENT`，也不再让 `fullPage()` 返回 >2 行后空屏。
3. **流式预览**：`RebuildCueContract.partialUnits()` 只发布“已完整覆盖的 group”；未完成的
   cue/group 不提前上屏，但前面的 group 不必等整块 reply。这缩短了人工源首条字幕的等待，
   同时保留 cue 原子性。

## 2. 问题二：现行逻辑没有全语种适配

### 2.1 证据：语言被编码成“是不是中文”

修复前的生产探针（`validation/runs/20261019-n42-root-cause/TmpN42ProbeTest.java`）：

```text
SPEC zh-Hans legacy=true  compact=true  cps=9  cpl=16
SPEC ja      legacy=false compact=false cps=4  cpl=13
SPEC en      legacy=false compact=false cps=20 cpl=42
SPEC ar      legacy=false compact=false cps=20 cpl=42
SPEC th      legacy=false compact=false cps=17 cpl=35
SPEC hi      legacy=false compact=false cps=22 cpl=42
```

对应代码：

- `CaptionRenderSpec`：`compactScript = chinese; legacy = chinese;`
- `RebuildPageLayout.plan()`：`if (spec.legacy) { … }` 才走中文的 clause/measured 路径；
  其它语言直接走 `CaptionLanguagePager`。也就是说，中文和所有其它语言不是同一套分页器。
- `RebuildDisplayGroups.separator()` 与 `RebuildCueContract.separator()` 各自写死
  `spec.compactScript || "ja".equals(...)`；韩语、泰语等没有空格文字被当成有空格文字。
- `RebuildReview` / `RebuildSemantics` / `RebuildPlanner` 的大量检查以
  `context.canApplyEnglishToChinese` 为条件。探针直接对 `ja→zh` 的错误译文调用生产
  `RebuildReview.inspect()`：

```text
JA_ZH_REVIEW_ISSUES=0
```

  即 `ja→zh` 几乎没有质量门禁；`RebuildSemantics.validate()` 第一行就是
  `if (!context.canApplyEnglishToChinese) return;`。
- `RebuildNumbers` 用英文月份/中文日期和 `canApplyEnglishToChinese` 分支；`zh/ja/ko` 之外
  没有目标文字检查（`validateTarget` 只写死 zh/ja/ko）。
- `CaptionLanguageProfile` 只枚举 14 种目标；未列出的语言落到 generic，但 generic 的
  行宽/阅读速率是否适合该文字没有机制保证。

### 2.2 根因层次

- **直接原因**：`compactScript`、`legacy` 两个布尔值由 `chinese` 派生，不是由 Unicode
  script 派生；语言对质量门禁由 `canApplyEnglishToChinese` 派生。
- **结构原因**：presentation 没有“script profile”对象；语言特例散落在分页、分隔符、质量
  检查、数字比较、提示词五个位置，每增加一种语言就要再写一个特例。
- **设计原因**：把“中文调优”当成“中文算法”，而不是“用 script 属性表达的中文参数”。
  日语此前的专门优化（`minimumPageMs=500`、`referenceCps=4`、`FINAL_PARTICLES` 中的
  日语/韩语助词）是数据/特例混在算法里，无法自动推广到韩语、泰语、阿拉伯语等。

### 2.3 根修方向（已实施）

1. **一个分页器**：`RebuildPageLayout.plan()` 对所有 target 调用
   `CaptionLanguagePager.plan()`；删除中文 `legacy` 分支（以及只被它使用的 DP/代价搜索）。
   `CaptionRenderSpec.legacy` 字段删除，缓存不再按语言选择算法。
2. **Script 事实对象**：新增 `CaptionScript`（caption-shared），用 ICU `UScript` 判断：
   - `compact`：Han/Hiragana/Katakana/Hangul/Thai/Lao/Khmer/Myanmar 不写词间空格；
   - `requiresSpace(left,right)`：两个 compact 文字紧排；compact + Latin / Latin + Latin
     需要空格；标点不额外加空格；
   - `primary(locale)`：目标主 script，用于目标文字门禁。
3. **分隔符统一**：`RebuildDisplayGroups` 与 `RebuildCueContract` 都调用
   `CaptionScript.requiresSpace`；compact script 的无标点事件连接仍用 U+200B 作为不可见
   页切点（screen 上不占格），有标点时不加。
4. **质量门禁去语言特判**：
   - `RebuildSemantics.validateTarget()` 对 zh/ja/ko 保留细检查，其它目标按 ICU script
     拒绝“整段是另一种文字”的译文（阿拉伯语目标收到拉丁文、印地语目标收到拉丁文等）；
     源文回声检查对所有语言对生效。
   - `RebuildSemantics.validate()` 的数字范围检查去掉 `canApplyEnglishToChinese` 前置。
   - `RebuildReview` 的 `dependent_boundary`、`invented_sentence_end`、`fragmented_plan`
     去掉 en→zh 前置；`invented_sentence_end` 现在对 `ja→zh` 也会产生 advisory。
   - `RebuildPlanner.dependentEnding()` 增加 CJK 虚词集合（日/韩/中），不再只对英语源
     启用；`strongDependentEnding/protectedCut` 仍只对英语做硬检查，避免对无词边界语言
     产生新的误拒。
   - `RebuildNumbers` 改为 Unicode 数值解析（见问题四），不再按语言对分支。
5. **参数而非算法**：`CaptionLanguageProfile` 仍是数据表（中文 9/16、日语 4/13、韩语
   12/16、generic 17/42 等），但分页/分隔/质量检查不再读取“目标是不是中文”。未列出的
   语言至少获得 generic 参数 + 正确 script 行为。

残留：`referenceCps/referenceCpl` 仍是人工参数，日语 4 cps、500 ms 最小页是否最优需要
母语验收；本轮不做“所有语言统一参数”的伪平均。

## 3. 问题三：字幕显示所需的时间偏长

### 3.1 诊断量化

对 123 个可见帧去重后得到 98 个唯一页帧（同一 id/page/text 的 hold 重复只计一次；
`REBUILD_PRESENTED` 的 `page_range`）：

| 页时长 | 页数 |
|---|---:|
| <1.2 s | 2 |
| 1.2–2 s | 12 |
| 2–3 s | 25 |
| 3–4 s | 31 |
| 4–5 s | 19 |
| 5–7 s | 8 |
| ≥7 s | 1 |

最长：7,439 ms（`43:1:5:314-333`，32 字，4.3 字/s）、6,788 ms、6,736 ms、6,584 ms。
`REBUILD_PRESENTATION` 只打印 `page_duration_above_recommendation`，7,439 ms 那条为 true；
6.7 s 的页面因为硬上限是 7,000 ms 而显示 false。覆盖层 `CaptionOverlayV2` 在最后一页
结束后还会 `END_HOLD_MS=800 ms` 保持。

首帧延迟（`REBUILD_SELECTED`/`REBUILD_PRESENTED` 的 `render_position - page_range.start`）：
87/98 页 <250 ms；只有首块/首字幕和 seek 后的重建出现 1.5–3.6 s 延迟。因此“显示时间偏长”
主要不是网络延迟，而是**单页停留时间**；首条字幕的冷启动延迟是另一个可优化点。

### 3.2 根因：页规划是几何优先，时间没有参与“单页是否该切”的决定

`RebuildPageLayout.unitPages()` 修复前：

```java
if (fitsOne.test(text) || spec.authored && fitsTwo.test(text))
    return singleton(new Page(text, start, end, ...));  // ← 整个 unit 窗口
```

只要文本能放进一行（人工两行），就直接返回单页，页的 `start/end` 就是 unit 的完整窗口。
`preferredLegacyPlan()`/`CaptionLanguagePager.choose()` 里虽然有 `timingCost`/
`softPageDurationMs`，但**只有 unit 放不下时才走到**。7 s 的 `softPageDurationMs` 只是
诊断字段，从未据此切页；`CaptionOverlayV2` 也没有“单页最大停留”逻辑。

于是页面时长由事件/合并单元的源窗口决定：32 字 7.4 s、27 字 6.8 s 都成一页。阅读速率
4–5 字/s，并不是字太密，而是“一页静态文字跟完 7 s 语音”。

### 3.3 根修方向（已实施）

在 `unitPages()` 中增加“时间平衡”分支，但只在**语义上可切**时生效：

1. 计算 `comfortMs = clamp(阅读时间 × 1.5, 3000, 5000)`；阅读时间 =
   `readingUnits / referenceCps`。只有阅读时间 ≥2 s（短译文不值得切）且
   `duration > comfort` 才考虑切。
2. 目标页数 = `ceil(duration / comfort)`，上限为“内部标点数 + 1”和
   `duration / MIN_PAGE_MS`。
3. `balancedPages()` 在完整分句边界上做小规模划分，优先一行、惩罚引子页/残尾，按阅读权重
   分配时间；任何一页估计不足 2.2 s 就放弃切分，宁可保持单页，避免 1.8 s 引子 + 5.6 s
   正文的坏切法。
4. 单个分句本身超过两行时仍只在分句内部 emergency split；单个分句即使 7 s 也不为了时长
   硬切（`aLongUnbrokenClauseStaysOneTwoLinePage` 回归保留）。
5. 人工 cue 只要 ≤2 行仍保持 cue 原子性；>2 行走 overflow 子页（问题一）。
6. 人工源流式预览改为“完整 group 即显示”（问题一），缩短块级等待。

探针（真实中文、2 个完整分句、7,000 ms）：

```text
LONG_FITTING_PAGES=2
```

单分句 9,600 ms 仍为 1 页（语义不可切）。诊断中的 7.4 s 页如果是“引子 + 一个长分句”，
可能仍保持单页；这是语义优先的边界，不是遗漏——不应为了缩短停留而把分句从中间切开。

## 4. 问题四：特定语句没有译文、显示“翻译中…”

### 4.1 证据 A：数字校验把正确译文当成替换（session 66，block 2）

诊断：

```text
1792404385175 | REBUILD_EVENTS_REJECTED | block=2;reason=numeric_substitution;session=66;request=71;attempts=1
1792404388578 | REBUILD_EVENTS_REJECTED | block=2;reason=numeric_substitution;session=66;request=72;attempts=2
```

质量证据 request 71/72 的同一源片段的译文：

```json
{"from":201,"to":214,
 "source":"like 4 and a half times the price with a flagship phone these days",
 "text":"大约4.5倍的价格买旗舰手机，到底多得到了多少。"}
```

复现（修复前）：

```text
RebuildNumbers.compare("like 4 and a half times the price", "大约4.5倍的价格", en→zh)
= CONTRADICTED
```

原因：`RebuildNumbers.safe()` 只提取“整数/小数”，`4 and a half` 提取成 `4`，`4.5` 提取成
`4.5`，两边各一个数字，`4 != 4.5`，于是 `numeric_substitution`。这是**数值的表示形式**
差异，不是替换。`4.5` 是源文 `4 and a half` 的正确值；校验器却按字面比较。

后果：整块 8 条事件全部丢弃；block 2 覆盖的 cue 只能显示“翻译中…”，慢重试仍然重复同一
判断，因为模型每次都会把 `4 and a half` 译成 `4.5`。

### 4.2 证据 B：碎片 cue 的跨 cue 合并（session 1，block 12）

见 1.2。请求 24/25/33/35 四次 `authored_cue_boundary`，原因都是 `range=868-871;
merges cue 47 into cue 48`；实际 cue 47 是 `が`，cue 48 是 `しかし`。模型合并是正确的；契约
把“作者 cue”当成不可合并的页，导致整块 150.250–157.167 s 不发布。四个 waiting 帧
（`1:3:waiting:12:…`、`1:5:waiting:12:…`、`1:6:waiting:12:…`）覆盖这 6.9 s。

### 4.3 证据 C：block 级 all-or-nothing 与无上限 placeholder

- `translate()` 只有完整 `Plan` 才写入 `s.plans[i]`；一个 event 失败，整个 block
  （人工 4 cue / 自动 8–11 event）都不发布。
- `render()` 在 `p == null || provisional` 时按源 cue 显示 `caption_translating`；
  `WAITING` 的结构性失败会慢重试（15 s 间隔），`FAILED` 只用于配置错误/content filter。
  因此结构性失败可以无限“翻译中…”，没有超时、没有降级页。
- 诊断无法直接看出 block 2 的数字值，因为旧 `numeric_substitution` 没有 range/values；
  本轮把 `range` 和 `source_values/target_values` 写进 `REBUILD_EVENTS_REJECTED`。

### 4.4 根修方向（已实施）

1. **数值按值等价**（`RebuildNumbers` 重写）：
   - 支持分数/半：`4 and a half`、`one and a half`、`4½`、`四个半`、`3/4`；
   - 支持全角/阿拉伯-印度数字、分组逗号、小数；
   - 支持数量级：`1万`、`1.5万`、`10k`、`2 million`、`3 billion`；
   - 日期仍用原有 en/zh 日期等价；多数字/缺数字保持 `UNKNOWN`，不硬拒；
   - 只有“两边各一个可解析数值且值不同”或日期明确冲突才 `CONTRADICTED`；
     其它情况最多 advisory。
2. **Cue 碎片分组**（见问题一）：`が`+`しかし` 变成 display group，模型合并落在 group 内；
   实际 `b12_868_892` 从“4 次拒绝”变为 `PARSED events=3; UNITS=2`。
3. **人工流式 partial**：完整 group 可先显示，未完成 group 等待；减少 block 级等待。
4. **数字拒绝诊断**：`REBUILD_EVENTS_REJECTED` 新增 `range` 与
   `source_values/target_values`，下次可直接定位是哪个数。
5. 保留“任何情况下不显示源文”的 N41 约束：失败时空白或中性占位，不回退原文。

## 5. 四条问题的共同根因

| 层 | 修复前的事实 | 后果 |
|---|---|---|
| 显示权威 | 人工 cue、模型 event、display group、page、overflow 子页是四套身份 | cue 可被 event 拆；overflow 可空屏/截断；页数随模型输出变化 |
| 语言权威 | `chinese` 布尔值决定分页器/分隔符；`canApplyEnglishToChinese` 决定质量门禁 | 非中文目标走另一套算法；ja→zh 几乎无门禁 |
| 质量门禁 | 数字按字面；block 级 fail closed；失败无降级 | 正确译文被丢；整块“翻译中” |
| 页时间 | 能放进一行/两行就返回单页，时间只在“放不下”时参与 | 5–7.4 s 静态页；softPageDuration 只是诊断 |

更根本地说：**没有一个“显示契约”对象同时承载 cue/group、页、overflow、语言 script 和
时间预算**。N41 建立了 cue 契约，但它仍把 cue 当成唯一页；N40/N41 的语言特例仍散落在五个
文件。本轮把“显示页”提升为单一投影：输入是 group/cue + 译文 + 时间窗 + 几何，输出是
页/子页，所有语言走同一个 planner；质量门禁改为 script/数值事实，而不是语言对布尔值。

## 7. 边界与未决

- 未连接/未安装手机；本轮是只读诊断 + 离线生产代码探针 + JVM 测试，真机 after 诊断待
  用户复验。
- 翻译语义仍由供应商模型决定；本轮只保证“不因格式/数值/分组误判丢弃正确译文”，不新增
  语义裁判。
- 人工 cue 的“碎片”判定是保守集合（虚词/极短/极短时长），可能仍有作者认为可独立成页的
  2 字 cue 被合并；阈值可在真机 after 诊断中调整。
- 单个分句超过两行时只能在分句内部 emergency split；这是“不空屏”与“不断语义”的明确
  取舍，不是遗漏。
- 数值等价仍不解析所有语言的数词（如中文 `二十`、阿拉伯语数词）；这些情况保持
  `UNKNOWN`，不会硬拒，但也不会被证明等价。
- `referenceCps/referenceCpl` 的语言参数仍需母语验收；本轮只去掉“语言决定算法”的结构。
